# リカバリ・並行制御・DDL 競合と JOB J3 の20題

リカバリ6件、並行制御4件、DDL 6件、JOB 4件を `RestartRaces` 以下の `Goal : Prop` として公開した。以下の表は1行が1つの実装判断に対応する。具体的な入力に対する検査は別にしている。末尾に保存済みベンチマークの計測条件と追試を載せた。

## リカバリ

現行の復旧は検証済み WAL を2回読み、commit 済み所有者を選んで LSN 順に再生する。チェックポイントは WAL の durable target を待ち、公開後に replay anchor より古いセグメントを回収する。以下はこの契約を維持したままどこまで処理を省けるかを問う。[復旧の契約](../../../docs/recovery_invariants.md)・[復旧実装](../../../recovery/recovery_manager.cpp#L842)・[Lean 定義](../../TinylambOpt/ResearchGoals/RestartRaces/Recovery.lean)

| 命題 | 実装判断と適用境界 |
|---|---|
| `DestroySummary` | WAL の第1走査をセグメントごとに並列化する。所有者・ページごとの最終 destroy LSN を保持し、全セグメントの commit 集合が揃ってから照合すれば、正確な再利用境界と次の取引 ID の基になる最大値を得られるか。未完了所有者も最大 ID に数える。 |
| `DemandRedo` | 最初に要求されたキーから WAL を逆向きにたどり、必要な初期ページと redo だけを読み込む。完全な上書きは依存を消し、別キーからのコピーは依存先を移す。すべての初期値で正しく、かつ必要な初期キー集合が最小か。 |
| `CommitDrain` | 1走査で取引ごとに保留し、commit 到着順に反映する。各キーについて WAL 順の最終勝者と最後に commit する書き手の一致が、任意の完全な after-image で同じ結果を得るための必要十分条件か。 |
| `FuzzyTransfer` | 2ページにまたがる符号付き振替を、ページごとの LSN で独立に再開する。各ページが別の位置まで反映されたチェックポイントと、再生途中の再クラッシュを経ても残高が一致するか。読者への公開は両側が準備できた後を想定する。 |
| `RetentionProbe` | 長時間取引に pin された WAL を置換するとき、未確定取引の全 commit 部分集合を検査する代わりに「全件 abort」と「各1件だけ commit」を照合すればよいか。対象はキーごとに独立な完全 after-image と世代を識別する stamp。差分更新・コピー・所有者 ID の復旧は別途必要になる。 |
| `GenerationGC` | 世代付き checkpoint にフォールバックを導入する場合、許容する各クラッシュ時点で実際に選ばれ得る世代の sidecar だけを残せるか。選択に必要なファイル、manifest、保持 WAL 区間を含める。稼働中の読者の pin は別に守る。 |

## 並行制御

行単位の write intent や待機グラフを細分化する案と、現在より強いコミット検証を加える案を含む。観測対象を値に限定できる場面と、実時間での同時性が必要な場面をそれぞれ定義した。[トランザクション実装](../../../transaction/transaction_manager.cpp)・[既存の待機サイクル命題](../../TinylambOpt/ResearchGoals/EngineBoundaries/WaitCycles.lean)・[Lean 定義](../../TinylambOpt/ResearchGoals/RestartRaces/Concurrency.lean)

| 命題 | 実装判断と適用境界 |
|---|---|
| `BatchOCC` | 同じ snapshot を読んだ取引群を一括検証する。書込キーが互いに素なら、読者から「その値を変える書き手」へ張った辺の非循環性で、全読取りを再現できる直列順の存在を特徴づけられるか。同値書込み、削除、write skew を含み、範囲述語は対象外。 |
| `CycleInstant` | detector が全シャードを同時にロックせず、世代付き待機辺が連続して有効だった時間区間を採取する。候補サイクルの全辺が同時に存在したと断言できる境界は、区間の共通部分の有無か。 |
| `PackedWrites` | 同じ物理ワードの別フィールドへの更新を共存させる。相手の読取値を変えず、重なる書込みは同値なら、どちらの直列順も両者の読取値と最終値を保つか。単一ワードの原子的な定数代入が前提。 |
| `RangePromotion` | predicate lock のスロット不足時に区間へ昇格する。区間ごとの待ち件数を最小化すると、異なる待機取引の数は真の最適値の何倍までか。1取引が触れる区間数の上限を係数にする仮説。比較する候補は同じキーを保護し、同じスロット予算を満たす。 |

## DDL とカタログ競合

現行の `CreateIndex`、参照元のある表への DROP・RENAME の検査、snapshot と epoch に基づくカタログキャッシュを接続先に選んだ。オンライン index build、複数名の一括 rename、cascade は提案するプロトコルとして扱う。[カタログ変更](../../../database/database.cpp)・[snapshot とキャッシュ](../../../database/transaction_context.cpp#L121)・[Lean 定義](../../TinylambOpt/ResearchGoals/RestartRaces/Catalog.lean)

| 命題 | 実装判断と適用境界 |
|---|---|
| `OnlineUnique` | UNIQUE 索引を作りながら更新を通す。RID ごとの走査時刻より後の変更だけを集め、該当 RID の旧エントリを捨て、最後の新キーを戻す。公開時点の全走査と索引の多重集合・一意性判定が一致するか。NULL は一意性対象外、RID は世代込み、差分収集から公開までに隙間がないことが前提。 |
| `CascadeFence` | DROP CASCADE の依存閉包を DDL 競合後に再利用する。旧集合から新しい外向き依存がなく、集合内の全オブジェクトがまだ根から到達可能、という2条件は必要十分か。根から切り離された循環参照も検出する。 |
| `RenameMoves` | 互いの旧名を使う一括 rename を、一時名1つで実行する。空き名への move の最小回数は「変更名数＋非自明な置換サイクル数」か。中間名を外に公開せず、外部参照は同じ DDL 取引で更新する。 |
| `InstantDefault` | 列追加後も旧行に残る欠落スロットのため、過去の DEFAULT をいくつ保持する必要があるか。同じ schema から同時に見えて異なる値を要求する epoch だけに異なる番号を割り当てれば、選んだ個数の辞書スロットで全読取りを復元できるか。明示的に書かれた NULL は物理値として保持する。 |
| `ShadowBind` | prepared plan の名前束縛を部分再検証する。以前ヒットするまで探索した名前空間を再読すれば、残りの名前空間がどのように変わっていても同じオブジェクト世代・型に束縛されるか。手前への同名表追加、DROP、以前の不在を区別する。 |
| `UniqueHandoff` | 変更前後とも UNIQUE が成立する取引群を個別に公開できるか。旧所有者から新所有者へのキー引渡しに順序を付けられることが必要十分か。2取引でキーを交換すると、一括公開は可能でも、どちらを先に公開しても一時的に重複する。 |

## JOB で差が出たクエリと中間件数

2026-11-25 のリポジトリ内 JOB-style fixture、scale 10、8スレッド、warmup 1回、計測3回の中央値（ms）。5問すべてで両エンジンの結果ハッシュが一致した。これは生成データの5問比較で、標準 IMDb JOB 全体の成績を表すものではない。[クエリと生成器](../../../benchmark/comparison/analytics_bench.py#L203)・[保存済み計測](../../../build/benchmarks/analytics-sf10-waves1-13/results.jsonl)

| | J1 | J2 | J3 | J4 | J5 | 中央値の合計 |
|---|---:|---:|---:|---:|---:|---:|
| tinylamb | 4.817 | 9.907 | **23.070** | 14.971 | 7.558 | 60.323 |
| DuckDB | 5.060 | 10.074 | **8.885** | 16.460 | 9.799 | 50.278 |

J3 は配役から対象の役柄を選び、女性の人物および条件に合う映画と結合して `COUNT(*)` と製作年の `AVG` を返す。元の CSV を再読して次を確認した。

- 配役2,000,000行のうち役柄で999,750行が残る。人物 ID は1～20,000の20,000種類、映画 ID は400,445種類だった。人物・映画ペアは993,816種類もあり、役柄で絞った直後に完全一致ペアを束ねても減るのは5,934組分。
- 人物条件を先に適用すると325,495行、映画条件を先に適用すると244,011行が第2の結合へ進む。一方、映画を先に通しても参照が必要な人物は19,963種類で、人物 ID を256個ずつ区切った79区画にまたがる。これは論理キー区画の数であり、ストレージの実ページ I/O 数は未測定。
- 最終結果は79,291行分、年の総和157,120,459、平均1981.5673783909901。人物側の一致件数を重みとして映画ごとに配役を束ねる別の SQL でも一致した。ここで特定できたのは処理行数と偏りで、14.185 ms の差に対する各演算子の寄与は未測定。[再集計スクリプト](fixtures/job_j3_census.py)

| J3 の命題 | 実装判断と適用境界 |
|---|---|
| `ProbeSchedule` | 各 morsel で、今の正確なキャッシュミス数が最小の側を先に probe する方針は全体でも最適か。2ブロックの具体例では局所方針が3ミス、全体最適が2ミス。最初の判断は同点でもない。負のキャッシュの将来再利用に価格を付ける動機になる。 |
| `PersonPages` | 映画側の結合多重度を先に得た場合、COUNT を決めるために必要な人物ページの最小集合を導く。人物属性が任意に変わり得る条件での情報量の下界。人物 ID の上限や欠番を安全に利用する候補。 |
| `RankOneTile` | 人物×映画の局所的な配役多重度を非負整数ベクトル2本の積に置き換える。すべての2×2小行列で対角積が等しければ、どの属性フィルタ・年重みでも COUNT や総和を正確に復元できるか。実データに採算の合うタイルがどれだけあるかは未計測。 |
| `DeltaRefresh` | J3 を継続的に読まれる集約として保持する場合、配役・人物・映画を同じ取引で変更しても、3本の疎な差分で更新できるか。各段で既に更新した軸を参照して交差項を取りこぼさない。COUNT・非 NULL 件数・年の総和を別々に計算し、実装時の整数幅と AVG 丸めを別途照合する。 |
