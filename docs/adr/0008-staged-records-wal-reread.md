# 大きなトランザクションはログの写しを捨てて WAL から読み戻す

Status: accepted（2026-11-16 決定、2026-11-17 P6a 実装済み: `transaction/transaction*.{hpp,cpp}`、既定 4 MiB）
決定者: ユーザーの委任による Claude の判断
関連: [`ooca-v2.md`](../../ooca-v2.md) §4 D6、[recovery invariants](../recovery_invariants.md)

## 背景

`Transaction::AppendLog` は、レコードを `Logger::AddLog` で WAL に追記したうえで、同じレコードを
`staged_records_`（`std::vector<LogRecord>`）にも積む。この写しは、実行時 Abort の巻き戻し
（`PageManager::ApplyTransactionAbort`）とコミット時の反映に使われる。件数に上限が無いので、
1 トランザクションの変更行数に比例してメモリを使う。

元の設計（`ooca.md`）はこれを「コミット時に一括フラッシュするバッファ」と説明し、
トランザクション用の一時 WAL ストリームを新設する案を出していた。実際には WAL に
同じ内容が既にあり、レコードは `prev_lsn` で鎖になっている。読み戻す手段もある。

- `Logger::TryCopyBuffered`: まだディスクに出ていないレコードをリングバッファから読む
- `RecoveryManager::ReadLog`: セグメントファイルから読む
- 実行中のトランザクションは、自分の最初の LSN より後ろの WAL セグメントの回収を止めている

## 決定

1. 写しの合計バイト数がしきい値を超えたトランザクションは、写しを捨てて
   「WAL 読み戻しモード」に入る。それ以降は写しを積まない。
2. しきい値以下のトランザクションは今までどおり写しを使う。短いトランザクションの
   経路と性能は変えない。
3. 読み戻しモードの Abort は、`prev_lsn` の鎖を後ろ向きに辿る。各レコードは
   `TryCopyBuffered` を試し、取れなければ `ReadLog` で読む。
4. 読み戻しモードのコミット反映は、自分の最初の LSN から前向きに WAL を走査し、
   自分のレコードだけを適用する。メモリは一定で、他のトランザクションのレコードを
   読み飛ばす I/O が増える。
5. トランザクション用の一時 WAL ストリームは作らない。

## 検討した案

| 案 | 採否 |
|---|---|
| トランザクション用の一時 WAL ストリーム（元文書） | 不採用。WAL にある内容の複製になる |
| Steal / No-Force ＋ CLR による undo（元文書） | 不採用。[ADR 0007](0007-uncommitted-pages-private-spill.md) のとおりリカバリ方式を変えない |
| 写しを `SpillStore` に追記する | 不採用。WAL と同じ内容を 2 回ディスクに書く |
| コミット反映用に LSN の列だけを `SpillStore` に追記する | 予備案。4 の走査量が問題になったら切り替える |

## 影響

- 実行時 Abort が WAL を読むようになる。`recovery_invariants.md` の
  「Runtime abort and replay」節は実装時に更新済み（WAL の prev_lsn 鎖を後ろ向きに読む記述へ）。
- しきい値の初期値は 4 MiB とし、`tx` プールの予約から払う
  （[ADR 0003](0003-memory-budget-thresholds.md)）。
- 読み戻しモードに入った回数と読み戻したバイト数を統計に出す。

## 採用条件

1 トランザクションでメモリ上限の 10 倍のデータを変更し、コミットと Abort の両方で
ログの写しのメモリがしきい値を超えないこと。読み戻しモードの Abort の途中でクラッシュ
させても、再起動後にコミット済みの状態だけが見えること。TPC-C に退行が無いこと。

## 見直す条件

コミット反映の前向き走査が、同時に走る他のトランザクションのログ量に引きずられて
遅くなる場合は、予備案（LSN の列を追記する）に切り替える。
