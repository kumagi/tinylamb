# 模索段階ではディスク形式の互換性を保たない

Status: accepted（2026-11-16）
決定者: ユーザー
関連: [`ooca-v2.md`](../../ooca-v2.md) §4 D9

## 背景

Out-of-Core 化では、TLCS のディレクトリ、ページディレクトリ、チェックポイント、
ブロックファイル、LSM のランなど、複数のディスク形式を変える可能性がある。
形式を変えるたびに旧形式の読み取りや変換を書くと、設計の試行錯誤が遅くなる。
現時点で保護すべき利用者のデータは無い。

## 決定

1. 今後の形式変更では、旧形式の読み取りも変換も維持しない。
2. 形式を変えたら、その形式のバージョン番号（またはマジック）を必ず上げる。
   旧形式のファイルは、内容を解釈しようとせず、明示的なエラーで拒否する。
   誤って読んで壊れたデータを見せることだけは避ける。
3. 既存の DB は再ロードする。ベンチマーク用のロード済み DB も作り直す。
4. TLCS ファイル（`<db>.tlcs.<first_pid>`）は行ページから再生成できる派生データとして扱い、
   バージョンが合わないものは捨てて作り直す。
5. 形式を変える変更には、[`docs/page_format.md`](../page_format.md) と
   [`docs/wal_format.md`](../wal_format.md) の更新を含める。

## 既存の ADR との関係

[ADR 0001](0001-fixed-wal-logical-end.md) は既存の WAL メタデータ v1 を変換せずに残している。
その扱いは、WAL 形式に次の変更が入るまで現状のままとする。次の変更からは本 ADR に従う。

## 影響

- 規模試験と最終ゲートは、その時点の形式で新しくロードした DB で測る。
  元文書（OOC-A 設計）の「既存のロード済み DB を再利用する」は採らない。
- ロードにかかる時間が試験の手間に乗る。TPC-H SF=100 などの大きな DB は、
  形式が変わる変更をまとめてから作り直す。

## 見直す条件

保持しなければならないデータを持つ利用者が現れたとき、または形式を安定版として
宣言するとき。そのときは本 ADR を置き換える ADR を書く。
