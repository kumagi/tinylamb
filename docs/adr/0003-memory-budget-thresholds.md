# メモリ予算の階層・しきい値・最小メモリ

Status: accepted（2026-11-16 決定、2026-11-17 P1 実装済み: `common/memory_budget.*`。比率は初期値で実測後に見直し可）
決定者: 最小メモリはユーザー。それ以外はユーザーの委任による Claude の判断
関連: [`ooca-v2.md`](../../ooca-v2.md) §1.4、§4 D1、§5.1

## 背景

現行の `ProcessMemoryBudget`（`common/memory_budget.*`）は次の値を持つ。

- 上限 `M`: `TINYLAMB_MEMORY_LIMIT_BYTES`、既定 16 GiB
- 追跡量のソフト上限: `M` の 80%
- RSS による打ち切り: `M` の 87.5%
- `kStorage` の上限 `min(4 GiB, M/4)`、`kColumnar` の上限 `min(2 GiB, M/8)`、`kQuery` は上限なし

これとは別に `QueryMemoryBudget`（`executor/query_memory.hpp`）がプロセス全体の
シングルトンとして実行用の上限を持つ。上限が 2 か所にあり、プール間で回収する仕組みが無い。
強制予約（確保した後で加算する）が非テストコードに 7 箇所ある。

元の設計（`ooca.md`）は「管理対象 85%、RSS が 90% で緊急退避」としたが、未追跡分に 15% を
見込みながら 5% 増えただけで緊急退避が走る値であり、現行コードの値とも合っていなかった。

## 決定

### 境界

| 境界 | 値 | 動作 |
|---|---|---|
| `M_t`（追跡量の上限） | `0.80 M` | 追跡対象の合計はここまで。超える予約は失敗する |
| RSS 警戒 | `0.875 M` | 新規の予約を失敗させ、回収フックを呼ぶ |
| `M` | `1.0 M` | 超えてはならない。超えたら不具合として調べる |

現行の値をそのまま使う。変えるのは、これを唯一のしきい値にすることである。

### プール

- プールは `storage` / `columnar` / `query` / `tx` の 4 つ。`tx` は新設する。
- 各プールに**下限**（他のプールに奪われない量）を持たせる。下限の合計は `M_t` 以下。
  残りは全プールで共有する。
- 下限の初期値は `M_t` に対して `storage` 25%、`query` 25%、`tx` 5%、`columnar` 0%
  （カラムナは純粋なキャッシュとして扱う）。
- 既存の `TINYLAMB_BUFFER_POOL_BYTES` と `TINYLAMB_COLUMNAR_CACHE_BYTES` は、上限の意味のまま残す。

### 回収

予約が通らないときは、次の順で回収を試み、最後まで通らなければ予約の失敗を返す。

1. カラムナのキャッシュを捨てる
2. クリーンなページを退避する
3. 実行中の回収可能な演算子にスピルを要求する（[ADR 0004](0004-query-memory-grants.md)）

回収フックは待たない。ラッチは `try_lock` で取り、取れなければその対象を諦める。

### 予約のしかた

- メモリを確保する前に予約する。ベクタやハッシュ表を伸ばすときは、新しい領域の分を先に予約する。
- 予約は 64 KiB〜1 MiB の単位でまとめて取り、スレッドごとに小分けにする。
- 必ず成功しなければならない小さな確保（エラー経路、カタログ、リカバリ）は、専用の小さな
  予備プールから払う。強制予約はこの用途だけに残し、呼び出し箇所を lint で固定する。

### 追跡漏れ

「RSS − 追跡量」を常時計測する。`0.075 M` を超えたら追跡漏れとして直す。

### 最小メモリ

サポートする最小の `M` は **1 GiB**。空の DB で `SELECT 1` を実行したときの最大 RSS は
約 42 MiB（CLI、Linux x86-64、32 論理 CPU、2026-11-16 実測）で、固定費は障害にならない。
負荷中の追跡漏れを `0.075 M`（1 GiB で約 77 MiB）に収められない場合は、比率を緩めずに
最小の `M` を 2 GiB に上げる（4 GiB までは許容されている）。

## 保証しないこと

OS の OOM Killer を確実に避けることは保証しない。RSS のサンプリングは間引かれており
（256 回に 1 回、または 2 ms ごと）、cgroup の下ではページキャッシュも数えられる。
保証するのは追跡量が `M_t` を超えないことまでである。

## 検討した案

| 案 | 採否 |
|---|---|
| 85% / 90%（元文書） | 不採用。上記のとおり定常的に緊急状態になる |
| プールごとに固定の割り当てだけを持ち、共有しない | 不採用。OLTP と OLAP でストレージと実行の比率が大きく変わる |
| RSS だけで制御する | 不採用。サンプリングの遅れの間に上限を超える |

## 影響

- `QueryMemoryBudget` は `query` プールを見る窓口になる（ADR 0004）。
- [`docs/environment_variables.md`](../environment_variables.md) に、プールの下限の変数を足す。
- [`docs/lock_order.md`](../lock_order.md) に「予約を呼ぶ側が保持してよいラッチ」と
  「回収フックが取ってよいラッチ」を足す。

## 見直す条件

- プール別の実測（`ooca-v2.md` の P0）が出たら、下限の比率を決め直す。
- 追跡漏れが `0.075 M` に収まらないことが分かったら、最小の `M` を上げる。

## 2026-11-17: 列キャッシュの既定上限の見直し

TPC-H SF 10のQ1では、既定2GiBの列キャッシュ上限で投影を保持できず、
毎回の準備に約2.7秒、フォールバック集約に約1.2秒を費やしていた。
保持可能な配分で同じ集約を実行すると約34msになった。
列キャッシュの既定上限を `min(8 GiB, M/2)` に変更する。
総予算16GiB、追跡量80%、RSS警戒87.5%、各プールの下限は変更しない。
実効上限には他プールの下限も適用されるため、空いている共有枠を使う変更である。
`TINYLAMB_COLUMNAR_CACHE_BYTES` を指定した場合はその上限を優先する。
1GiB・16GiBの予算で、大きな投影と他プールの下限を同時に予約でき、
列キャッシュの実効上限を超える予約が失敗することをテストする。
