# 未コミットの変更を持つページは専用スピル領域へ退避する

Status: accepted（2026-11-16 決定、2026-11-17 P6b 実装済み: ページ単位の `'TUPO'` 未コミットオーバーレイを `SpillStore` に退避）
決定者: ユーザー
関連: [`ooca-v2.md`](../../ooca-v2.md) §4 D5、[recovery invariants](../recovery_invariants.md)

## 背景

`PageManager::EvictBatch` が退避するのは、編集中の状態とコミット済みの状態が一致する
ページだけである（`RowPage::LiveEqualsCommittedLocked()`）。1 トランザクションが大量の行を
変更すると、触ったページは全てコミットまで RAM に残る。書き込みセットやログの写しを
ディスクへ逃がしても、ページ本体が変更行数に比例して残るので、大規模な UPDATE / DELETE /
INSERT はメモリ上限を守れない。

一方、リカバリは「コミット済みトランザクションのレコードだけを再生する」方式で、
再起動時の undo も、永続化された DPT / ATT も持たない。本体ファイル（`<db>.blocks`、
`<db>.db`）にはコミット済みの状態しか書かれない、という前提の上に成り立っている。

## 決定

1. **未コミットの状態を本体ファイルに書かない。** 現行のリカバリ方式を保つ。
2. 未コミットの変更を持つページを退避するときは、コミット済みの状態との差分
   （オーバーレイ）を `SpillStore`（[ADR 0005](0005-spill-store-placement.md)）上の専用領域に書く。
   コミット済みの状態は従来どおり本体ファイルから読み直せるので、RAM からは両方を落とせる。
3. ページを再び読むときは、本体ファイルのコミット済み状態にオーバーレイを重ねて復元する。
4. Abort は、退避済みページについてはオーバーレイを捨てるだけで済む。
5. クラッシュ時は専用領域ごと捨てる。再起動の手順は変わらない。

## 検討した案

| 案 | 内容 | 採否 |
|---|---|---|
| A | 上記 | 採用 |
| B | ARIES 型の steal。未コミットの状態を本体に書き、再起動時に undo する | 不採用。リカバリを作り直すことになり、`recovery_invariants.md` の前提が全て変わる |
| C | 大量挿入だけを新しいページ列に書き、コミット時に見えるようにする | A と併用する候補。INSERT / COPY には効くが UPDATE / DELETE には効かない。設計するときに別の ADR にする |

## 未決の点

- 専用領域の単位。1 ページに複数トランザクションの未コミット変更が載りうるので、
  「ページ単位のオーバーレイに、変更ごとのトランザクション ID を付ける」形を第一候補とする。
  トランザクションごとに領域を分ける形は、同じページを複数回書くことになる。
- コミット時の反映。退避済みページへの反映は、ページを読み戻して行うか、
  オーバーレイをコミット済み状態として本体ファイルへ書き出すかを実装時に決める。
  どちらでも、本体へ書くのはコミットの WAL が耐久化された後に限る（WAL-before-data）。

## 影響

- `EvictBatch` の退避条件と、ページの読み戻し経路（`EnsurePageResident`）が変わる。
- `recovery_invariants.md` に「未コミットの状態は一時領域にだけ書かれ、再起動で破棄される」を足す。
- [`docs/lock_order.md`](../lock_order.md) に、オーバーレイ書き出し中に保持してよいラッチを足す。
- 専用領域のディスク使用量は、スピルのディスク上限に含める。

## 採用条件

1 トランザクションでメモリ上限の 10 倍のデータを UPDATE / DELETE し、コミットと Abort の
両方が上限内で終わること。途中でクラッシュさせた後の再起動で、コミット済みの状態だけが
見えること。既存のリカバリ試験と TPC-C に退行が無いこと。
