# ページディレクトリは段階的に小さくする

Status: accepted（2026-11-16 決定、2026-11-17 段階 1 実装済み: `EvictedPageTable` / `BoundedFreeIdSet` / `LsmBlockCache` in `page/page_lsm_store.*`。段階 2 は未着手）
決定者: ユーザーの委任による Claude の判断
関連: [`ooca-v2.md`](../../ooca-v2.md) §4 D7、§5.4、[ADR 0010](0010-resident-pages-by-bytes.md)、
[ADR 0011](0011-no-on-disk-compatibility.md)

## 背景

`PageManager::blocks_` は全ページの `Page` オブジェクトを持ち続ける。ペイロードを退避しても、
`Page` と `RowPage` の本体（ラッチ、ベクタ、ディスク上の位置など）は残る。ほかにも
ページ数に比例するものがある（`eviction_fifo_`、`BoundedFreeIdSet`、
`WriteCompactedBlocksFile` に渡す全ページのベクタ、チェックポイントで書き出す全ページのメタ）。

元の設計（`ooca.md`）は「チェックポイントのメタを固定チャンクで逐次書く」と
「ディレクトリ自体をページ化して退避可能にする」を両方挙げていた。ディレクトリが
永続化されれば、チェックポイントで全ページのメタを書き出す必要は無くなる。
一方で、ディレクトリ自体のクラッシュ一貫性と、ディレクトリのページを読むために
別のページの退避が要る場合の扱いは書かれていなかった。

非常駐ページ 1 枚あたりの実際のバイト数は、まだ測っていない。

## 決定

### 段階 1（確定）

- 非常駐ページについて RAM に残すのは「ページ ID → ファイル上の位置と長さ」だけにする。
  `RowPage` の本体は常駐している間だけ存在する。
- `eviction_fifo_` と `BoundedFreeIdSet` も、ページ数に比例して伸び続けない形にする。
- チェックポイントとブロックファイルの再編成は、ページを 1 枚ずつ処理し、
  全ページ分のベクタを作らない。
- ディスク形式は変えない。

### 段階 2 へ進む条件

段階 1 の後で、目標規模（1 TB）での記述子の合計が `M` の 1% を超えると実測で分かった場合に進む。

### 段階 2（方針のみ）

- ディレクトリを永続化し、常駐させるのはルートだけにする。
- 専用の B+Tree を新しく作る前に、ディスク上の LSM の 1 インスタンスとして持つ案を検討する。
  ブロックファイルが追記型なので相性がよく、新しい構造が 1 つ減る。
- ディレクトリ用のメモリは `storage` プールの中に専用の下限を取り、通常ページの退避が
  ディレクトリの読み込みを待たないようにする。
- 互換性は保たないので（ADR 0011）、ブロックファイルとチェックポイントの形式は一から決めてよい。
- 形式とクラッシュ一貫性の方法は、進むと決めた時点で別の ADR に書く。

## 検討した案

| 案 | 採否 |
|---|---|
| 最初からディレクトリをページ化する（元文書） | 見送り。効果を測らずに形式とリカバリを変えることになる |
| チェックポイントの逐次書き出しだけ行う（元文書のもう一方） | 段階 1 に含めた。これだけでは RAM 上の記述子が残る |

## 影響

- `Page` を直接持ち回っているコード（`PageRef`）は、非常駐ページでは `Page` が
  存在しないことを前提にする必要がある。
- 再起動時に全ページの `Page` を作らない。チェックポイントの読み込みも逐次にする。

## 採用条件

DB サイズがメモリ上限の 10 倍のとき、ロード・チェックポイント・再起動・全表スキャンで
`storage` プールの追跡量が上限以下であること。TPC-C に退行が無いこと。
