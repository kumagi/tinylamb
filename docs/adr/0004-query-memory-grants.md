# クエリへのメモリ付与と演算子予算

Status: accepted（2026-11-16 決定、2026-11-17 P1/P3 実装済み: `common/query_grant.*`；なお項目 10 のプランナ予算は `plan/*_plan.hpp` に 64 MiB 既定定数が残存）
決定者: ユーザーの委任による Claude の判断
関連: [`ooca-v2.md`](../../ooca-v2.md) §1.4、§4 D2、[ADR 0003](0003-memory-budget-thresholds.md)、
[`TODO.md`](../../TODO.md) S2 / S10

## 背景

- `QueryMemoryBudget` はプロセス全体で 1 つの残量を全クエリ・全演算子が取り合う。
  後から動き出した演算子は残量が無く、最初からスピルする。
- 演算子の予算は固定値で決まっている箇所がある（`GroupedAggregate` の既定は 64 MiB、
  HashJoin のスピル分割数は 16 と 32、Window は 8）。同時に動く演算子の数は反映されない。
- 元の設計（`ooca.md`）は `B_op = floor(M_query / B_cnt)` としたが、同時に走るクエリ数を
  考えておらず、`M_query` が未定義で、動作に必要な最小量も決めていなかった。

## 決定

### クエリへの付与

1. 入力を溜めるシンクを持つクエリは、開始時に `query` プールから付与 `G_q` を受け取る。
2. 足りなければ待つ。時間切れで `kMemoryLimitExceeded`（[ADR 0012](0012-memory-limit-error-code.md)）。
   これが同時実行数の入場制御になる。
3. 点検索のように入力を溜めるシンクを持たないクエリは、付与を取らずに走る。待ち行列にも並ばない。
4. `TINYLAMB_QUERY_MEMORY_BYTES` は 1 クエリの `G_q` の上限として扱う
   （`docs/environment_variables.md` の記述「Per-query memory budget」に実装を合わせる）。

### クエリ内の配分

5. `G_q` は、その時点で入力を溜めているシンクだけで分ける。ビルドが終わったシンクの
   未使用分は次のパイプラインへ回す。
6. シンクは「回収可能」として登録し、調停側からのスピル要求にチャンク境界で応じる。
7. シンクの種類ごとに最小予算 `B_min` を定数として持つ
   （目安は「出力 1 チャンク ＋（分割数 ＋ 1）× スピルのブロックサイズ」）。
8. 1 ワーカーあたりの予算が `B_min` を下回るなら、並列度を下げる。並列度を決める場所は
   1 か所にする（`TODO.md` S10 の「DOP 決定の 1 か所」と同じ場所）。
9. 行サイズが演算子予算の 1/4 を超えてもスピルできる。符号化不能な行や分割不能な集約状態には `kTooBigData` を返す。

### プランナ

10. （未達）プランナがコスト計算に使うメモリ予算は、実行時付与と同じ場所から
    求める。実行時と別の定数を持たない。現状は `plan/aggregation_plan.hpp` /
    `sort_plan.hpp` / `window_plan.hpp` がそれぞれ 64 MiB の自前既定定数を保持
    しており、上記 Status 行の例外注記のとおり未実装である。

### 旧演算子

11. 旧演算子は付与を使わない。`QueryMemoryBudget` を `query` プールを見る薄い窓口として残し、
    今までどおりそこから取る。旧演算子と一緒に消す（[ADR 0006](0006-ooc-parts-on-new-sinks-only.md)）。

## 検討した案

| 案 | 採否 |
|---|---|
| 静的な等分（元文書） | 不採用。同時クエリ数を扱えず、ビルド済みの演算子の分が無駄になる |
| 全クエリが 1 つの残量を取り合う（現状） | 不採用。後発の演算子が不利になり、結果が実行順に依存する |
| 演算子ごとの固定値（現状の一部） | 不採用。同時に動く数が増えると上限を超える |

## 影響

- 最小メモリ（1 GiB）では、論理 CPU の多いマシンで並列度が自動的に下がる。
- 付与の待ち時間が新しい遅延要因になる。待った時間と付与量を EXPLAIN ANALYZE と統計に出す。
- 待ち行列の時間切れの既定値を決め、`docs/environment_variables.md` に書く。

## 見直す条件

付与待ちが OLTP と OLAP の混在で遅延の原因になった場合は、クエリの種類ごとに
`query` プールを分ける（短いクエリ用の予約枠を持つ）ことを検討する。
