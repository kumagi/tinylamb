## 遅さの原因と変更

**MVCCの履歴が、書き込み停止後に取り残されていた。** 大きな履歴はGCがshardを分割して回収するが、ワーカーは新しい書き込みcommitがないと次の回収をしなかった。最後のUPDATE後に読み取りだけになると、未回収のshardや、古いsnapshot／WAL待ちで保留した履歴が残り続ける。実測でも更新後に約7,500チェーンが残り、多数の行で高価な可視性解決を繰り返していた。

残る履歴がある間は100 msのタイムアウトで再回収するようにした。保持中の履歴をwait述語には入れず、古いsnapshotがある間もbusy loopにしない。1回の回収範囲、最古snapshotとWAL耐久性による保持条件は従来通り。最終版の100万行診断では、新しい書き込みがなくても残留チェーンが0になった。

**索引の小さな値に、汎用復号と多数のメモリ確保を使っていた。** INCLUDEなしの索引値は固定長の行位置と空Rowだが、候補ごとにstringstreamを作っていた。この形式だけ長さ・空要素数を確認して直接復号し、他形式や破損・切断データは従来の検査付き復号へ戻す。

葉ページの所有キャッシュも、エントリごとのstringから一つの連続領域とoffsetへ変えた。キャッシュ内のkey/valueは有効期間内だけviewで読み、PageRefや生のPageポインタを呼び出し間に保持しない。葉ページの連続化と短い範囲の先読み抑制を含む中間版・最終版で、同じ300回の範囲検索をCallgrindで調べると、命令数は344,561,006から140,446,794へ約59%減った。これはCPU命令数の比較で、実時間の高速化率ではない。[前](../benchmark/comparison/results/2026-10-29-read4-comparison/range-before-arena-inclusive.txt)／[後](../benchmark/comparison/results/2026-10-29-read4-comparison/range-final-inclusive.txt)を保存した。

**不要な復号・条件評価・先読み構築も重なっていた。** 非キー検索は約900〜1,000候補から10行を返すが、落とす行のpaddingまで復号していた。同じ型・符号の安全な整数／DATE比較を可視行のserialized imageで先に判定し、必要列だけ復号する。索引走査が既に保証する整数条件のSelectionを重ねず、短い範囲は二つ目の先読みカーソルを作らない。

連続して同じheapページに当たる読み取り専用の範囲走査は、共有ラッチ下でチェーンがないことを確認し、一ページ分の行イメージを所有コピーする。コピー後もReadVersionのエラー／可視性解決を保つ。ランダムなページ参照、書き込み可能なcontext、古いsnapshotで履歴が必要なページは通常の取得を使う。保持型索引や残差式、列順変更・重複など、射影の前提を満たさない形も通常経路を保つ。

## 正しさと検証

最終比較は**OLTP 72試行・OLAP 42測定**。SQLエラー、warmupエラー、試行無効、結果不一致は0件。周辺OLAPはCOUNT、SUM、Top 100、1%／10%選択、EXISTS、LEFT JOINを、両構成・3製品・9反復で照合した。この測定でフルベンチマーク全体を更新したわけではない。

計時ハーネスは非キー検索の返却ID列・balanceを毎回検証するが、従来のrange_readは返却SUMを個別検証していなかった。そこで計時外に独立した完全列挙を追加した。生成される始点0〜9,999の全範囲を両構成で検証し、値を変更してNULLを混ぜた後にも繰り返した。**40,000クエリが整数／NULLの厳密期待値と一致**した。[検証結果](../benchmark/comparison/results/2026-10-29-read4-comparison/range-correctness.json)。この完全列挙は性能測定の時間に含めていない。

全ctest **4,107件・失敗0**（既存skip 3件）、SQL oracle **301秒・456入力・不一致0**、Python解析31テスト、format 11ファイル、layeringを通過した。新しいallowlist登録はしていない。既存のindex_scan_iterator→tableの例外に当たるincludeが1辺増え、適用される既存allowlist辺は66になった。

追加した8テストは、heapキャッシュの範囲・穴・逆順、古いsnapshotと自分の更新、binary INCLUDEと葉境界、破損した固定長索引値、射影とパラメーター再束縛、NULL・符号・残差、GCの分割回収完了、最古snapshot終了後の回収再開を扱う。[検証ログ](../benchmark/comparison/results/2026-10-29-read4-validation/validation-manifest.json)。

## 測定条件と再現

サーバは共通の8論理CPU、buffer 512 MiB。tinylambはSQLワーカ8・query memory 64 MiB、PGはwork_mem 64 MiB。同期commitとWALの耐久性は変更していない。Simple Query・接続再利用・warmup 2秒・測定5秒を3試行実行した。最終測定は自分のbuild／ctest／fuzzer／プロファイラーを終了してから始めた。OSキャッシュは強制消去していない。
