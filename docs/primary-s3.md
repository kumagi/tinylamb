# Primary + S3：耐故障構成とローカル容量を超えるストレージ

**状態**　未実装の設計案（2026-11-26 全面改訂、2026-11-27 に 2 回のレビューを反映）。単一の writer と現行の単一 WAL ストリームを前提にする。[Raft・シャード構成の設計案](../distributed.md)とは独立している。プロトコルの核は TLA+ と Lean で検証した（§18）。

## 0. 要約

- **S3 を正本にし、ローカルディスクは WAL の送り出しバッファとキャッシュにする。** 書き込みを受ける primary は 1 台。SQL の結果は、それが依存するコミットの WAL が S3 に欠けなく保存されてから返す。初版の保証の対象は S3 Standard（汎用バケット）とする。
- **WAL はグループ PUT をパイプライン化して送る。** 条件付き PUT を最大 W 個（既定 8）同時に送り、S3 永続化 LSN は「先頭から欠けなく保存を確認できたチャンクの末尾」とする。処理量の上限は「同時 PUT 数 × 接続あたりの帯域」で、チャンクが大きいほどそれに近づく。チャンクの上限を 16 MiB に固定するので PUT の固定の遅延も効くが、遅延 30 ms なら上限の約 87% に届く（§16、Lean で証明）。遅い PUT は、ヘッジ専用の枠で重ねて送る。
- **TLCS 圧縮を primary で行う。** 圧縮で作った TLCS ファイルを先に S3 の不変オブジェクトとして保存し、チェーンの差し替えを WAL レコード `kInstallColumnar` として記録する。standby と復元は同じオブジェクトを使うので、行の配置が一致し、再圧縮も要らない（§8）。
- **ローカルディスクより大きい DB を扱える。** TLCS・LSM ラン・ブロックファイルの本体は S3 に置き、ローカルはその範囲キャッシュにする。ローカルに必ず置くのは、未送信の WAL、未アップロードのファイル、スピル、メモリ上の行ページだけ。ただし RAM 上のページ記述子は DB サイズに比例するので、規模の上限は [ADR 0009](adr/0009-page-directory-in-stages.md) の段階 2 で決まる（§10.5）。
- **writer の起動ごとにエポックを分け、封印は消さない。** 再起動と昇格では、直前のエポックを終端マーカーで封印してから次のエポックを作る。再起動したホストも、ローカル WAL を正式な履歴の末尾で切り詰め、未送信の末尾は捨てる。死んだ writer の PUT が遅れて届いても、旧 writer（ゾンビ）が生き残っていても、成功を返したコミットは失われない。この保証は旧 writer の隔離に依存しない。隔離が必要なのは、primary での読み取りの最新性だけである（§11）。
- **データオブジェクトの GC は時計に頼らない。** オブジェクトを消せるのは、それを作ったエポックが封印されたか、その writer が「以後参照を追記しない」と宣言した後だけである。アップロードの後に送信がどれだけ止まっても、正式な履歴が消えたオブジェクトを指すことはない（§13）。
- **応答のバリアの穴を塞ぐ。** 現行の D4 は、索引を引いて行が無かった読み取りの依存を記録しない。各コミットが索引・カタログの木ごとに「公開済み変更 LSN」を LSM への反映の前に上げ、読み取りはカーソルを開いた時点の値まで待つ（§7）。この修正はローカルモードにも効く。
- **検証の範囲。** 設計の各規則は、1 つ外すと TLA+ のモデルで違反が出ることを確かめた。大きさを限らずに言えること（履歴の単調性、起点から辿る走査、バリアの完全性、帯域とチャンクの大きさの関係）は Lean で証明した。遅延・PUT 数・コストの数値は、仮定した遅延分布での模擬実験による（§18）。設計時の検証で見つけた 12 件の穴と、2 回のレビューで受けた 24 件の指摘を、本文の規則に反映した（§18.5）。

## 1. 前提：現行の永続化と TLCS

### 1.1 永続ファイル

| ファイル | 中身 | 書き方 |
|---|---|---|
| `<db>.log`、`<db>.log.<20桁>` | WAL。レコード版 7、セグメントは既定 16 MiB | 追記。チェックポイントの再生開始点より下のセグメントを回収する |
| `<db>.db` | チェックポイントのスナップショット（`TLSMCKP1` v4）。コミット済みの行ページとリンク、LSM の項目、再生開始 LSN、トランザクション ID の上限 | 一時ファイルに書き、fsync して rename |
| `<db>.blocks.<gen>` | 退避した行ページの像 | 追記型。64 MiB を超え、かつ有効な部分が半分未満になると、チェックポイントで次の世代へ詰め直す |
| `<db>.lsm.<gen>` | 索引とカタログの LSM ラン（約 32 KiB の CRC 付きブロック） | チェックポイントのたびに次の世代へ書き直す |
| `<db>.tlcs.<first_pid>` | 表の列形式ファイル（TLCS v3） | 圧縮のたびに一時ファイルへ全体を書いて rename |

再起動では `<db>.db` を読み、再生開始 LSN から 2 パスで WAL を読む。1 パス目で `kCommit` のあるトランザクションを集め、2 パス目でそのレコードだけを再生する（[リカバリ不変条件](recovery_invariants.md)）。行の変更レコードは「ページ ID・スロット・行」を、LSM の変更は「木 ID・キー」を持つ（[WAL 形式](wal_format.md)）。

### 1.2 TLCS とは

TLCS は tinylamb の**永続列形式テーブルファイル**である。実装は [`table/tlcs_file.{hpp,cpp}`](../table/tlcs_file.hpp)、ファイル形式は [page_format.md](page_format.md) にある。

- **行の通常の置き場。** 行は `RowPage`（可変長のスロットを持つ行ブロック）に入る。表ごとに双方向リンクのチェーンになり、索引は行の位置（ページ ID とスロット）を指す。
- **圧縮。** `Database::CompactTableToTlcs` は表の全行を列ごとに符号化し直し、1 つのファイルにする。既存の TLCS があれば、それも読み直して全体を書き換える。
  - 1 ブロックは最大 32,768 行（`RowPage::kMaxColumnarRows`）。128 ブロックごとにディレクトリグループを置き、ブロックごとの行数、NULL の有無、列ごとのゾーンマップを持つ。
  - 列の符号化は、FOR、ビットパック、狭い辞書、前方圧縮辞書、フレーズ表、XOR（Gorilla 方式）、Zstd などから選ぶ（`TlcsColumnEncoding`）。末尾には列ごとの統計（単調性、一意性、最小値・最大値）がある。
- **スタブ。** 圧縮後、表のチェーンは**列形式スタブ**に置き換わる。スタブは行を持たない `RowPage` で、TLCS の 1 ブロックに対応する。行の位置は「スタブのページ ID・ブロック内の行番号」になり、索引はこの位置で作り直される。
- **読み取り。** ブロック単位で、必要な列だけを復号する（`ColumnarTlcsScanExecutor` など）。展開後の大きさが `min(columnar プールの上限 / 2, 1 GiB)` 以下なら mmap で、それより大きければ `pread` と上限付き LRU で読む。
- **書き込み。** スタブの行を UPDATE・DELETE すると、そのブロックを行形式に戻す（hydrate、`Table::EnsurePageHydratedIfStub`）。以後そのページは普通の行ページとして WAL で更新される。INSERT は末尾の行ページに入る。つまり TLCS は**圧縮済みの土台**、行ページは**変更の差分**として働く。
- **圧縮の前提と契機。** 対象の表に MVCC の版チェーンも進行中の書き込みもないこと（静止）が必要である。自動の圧縮は、`TINYLAMB_AUTO_TLCS`（既定で有効）によりチェックポイントの直前に、`TINYLAMB_ANALYZE_AUTO_TLCS` を指定したときは ANALYZE で走る。
- **永続化の順序。** TLCS ファイルを rename で公開し、索引を作り直し（LSM の変更として WAL に載る）、チェーンをスタブに差し替え（**WAL に載らない**）、多くの経路でチェックポイントを書いて確定する。スタブ化した後は、TLCS ファイルが行の唯一の実体になる（`PendingTlcsCommit::KeepTempFileOnDisk` の注記）。[ADR 0011](adr/0011-no-on-disk-compatibility.md) が「行ページから再生成できる派生データ」と呼ぶのは、版の合わない TLCS を捨てて作り直す方針のことである。

旧版の設計が primary での TLCS 化を禁じたのは、この差し替えが WAL に載らず、しかも行の位置を変えるからである。WAL だけを受け取る側は、圧縮後の「スタブのページ ID・行番号」を指す変更を、圧縮前の配置に適用できない。本設計は、差し替えを WAL に載せ、TLCS ファイル自体を S3 で共有して解決する（§8）。

### 1.3 耐久化の位置と D4

`Logger` は 3 つの位置を持つ。`BufferedLSN` はバッファへの追記の末尾、`CommittedLSN` はファイルへの書き込みの末尾、`DurableLSN` は fdatasync 済みの末尾である（[`recovery/logger.hpp`](../recovery/logger.hpp)）。[D4](commit_durability.md) では、コミットは耐久化の前に MVCC 版として公開される。読んだ側は、観測した版の `commit_lsn` を依存 LSN として記録し、応答の前にその耐久化を待つ。GC は、最新の `commit_lsn` が `DurableLSN` 以下になるまで版チェーンを消さない。コミットは、LSM の木（索引とカタログ）にコミット済みの状態を反映し（`ApplyTransactionCommitRecords`）、続けて版を可視にする（`CommitVersions`）。応答が待つ位置は、同期コミットなら自身のコミット終端と依存 LSN の大きい方、同期を切ったコミット（`Database::SetSynchronousCommit(false)`）なら依存 LSN だけである（`transaction/transaction_manager.cpp`）。

**現行の穴。** 依存 LSN を記録するのは、`TransactionManager` が版を読む経路だけである。索引を引いて項目が見つかれば、ヒープの版を読むので記録される（`index/index_scan_iterator.cpp`）。索引だけで答える経路（`IndexScanIterator::TryReadIndexOnly`）も、行のページに版チェーンが無いこと、つまり GC 済みで耐久化済みであることを条件にしているので、存在する行については安全である。しかし項目が無ければ、何も記録されない。このため、未耐久の DELETE の後に索引で引いて「0 件」を返した応答は、DELETE が失われたクラッシュの後で、存在しなかった状態を見せたことになる。TLA+ のモデルで再現した（§18.2、`barrier_version`）。§7 の規則で塞ぐ。

### 1.4 旧版から変えたこと

| 項目 | 旧版 | 本版 | 根拠 |
|---|---|---|---|
| WAL の送信 | 1 件ずつ直列に PUT | 適応型のグループ PUT を最大 W 個並行、遅い PUT はヘッジ専用の枠で重ねる | 直列は 1 接続の帯域で頭打ち（§16、§18.4） |
| primary の TLCS | 禁止し、行形式へ戻してから移行 | 許可。TLCS をオブジェクト化し、差し替えを WAL に記録 | §8 |
| standby | 正規配置へ復元し、そのコピーを再圧縮 | primary と同じオブジェクトと配置で WAL を適用 | §12 |
| ベース | 書き込みを止めて静止ベースを取得 | 通常のチェックポイントをオブジェクト化（停止なし） | §9 |
| ストレージ容量 | ローカルディスク以下 | S3 が正本、ローカルは範囲キャッシュ | §10 |
| 再起動 | 同じタイムラインを照合して再開 | 起動ごとに新しいエポック（封印してから作る）。ローカル WAL は正式な履歴の末尾で切り詰める | 同じ連番を使い続けると壊れる（§18.1、`same_epoch`）。未送信の末尾を使うと、読み取りと GC の保証が崩れる（`tail`） |
| 封印 | — | 消さない | 消すと、成功を返したコミットが失われうる（§18.1、`sealgc`） |
| 応答のバリア | 結果確定後の `BufferedLSN` まで待つ | 版の依存＋木ごとの公開済み変更 LSN | 不足と過剰の両方を解消（§7） |
| データのキー | 内容のハッシュを想定 | アップロードごとに新しいキー | GC と競合する（§18.3、`objgc_bug_dedupe`） |
| データの GC | — | マークの時点で確定済みのものだけを消す。時計を使わない | 時刻で判定すると、送信の停止が猶予を超えたときに参照先が消える（§18.3、`objgc_bug_timebased`） |

## 2. 目標・非目標・保証

**目標**

- G1：成功を返したコミットは、primary のプロセスやディスクを失っても新しい primary に残る。S3 同期モードでは、すべてのコミットを同期にする。
- G2：WAL の送信は帯域で律速され、S3 の往復時間では律速されない。具体的には、想定する遅延分布のもとで、物理リクエストを W＋ヘッジ枠に抑えたまま目標の WAL 量を持続できること（§16.1）。
- G3：primary で TLCS 圧縮と分析ができる。
- G4：DB の大きさがローカルディスクを超えられる。
- G5：standby は primary と同じデータオブジェクトを共有し、再圧縮しない。
- G6：指定したコミットへの復元（PITR）と、別クラスタとしての複製ができる。
- G7：死んだ writer の遅れた要求、ゾンビ writer、同時に走った複数の昇格操作、長い送信の停止に対して安全である。

**非目標**　複数 writer、障害の自動検知（昇格の手順は自動化できる形にする）、リージョンをまたぐ複製、Raft による合意。

| 事象 | 保証 | 依存する前提 |
|---|---|---|
| primary のプロセス停止・ディスク喪失 | 成功を返したコミットは残る | S3 のオブジェクトが保存され、読み出せること |
| 同期を切ったコミット | S3 同期モードでは受け付けず、同期に固定する。運用者が明示的に許したときだけ受け付け、その成功は耐久化を意味しない | なし。そのコミットを読んだ応答は §7 のバリアで待つ |
| ゾンビ writer（旧 primary が動き続ける） | 成功を返したコミットは失われない。ゾンビは新しいコミットに成功を返せない | なし（封印と、それを消さないことによる） |
| ゾンビでの読み取り | 古い状態を返しうる | 隔離かリースで防ぐ（§11.3） |
| S3 の一時障害・長い停止 | 新しい成功応答は待たせる。確認済みの範囲で済む応答は返る。WAL は捨てない。再開の後も、停止の前に作ったオブジェクトへの参照は解決する | ローカルディスクの空き |
| AZ 障害 | S3 Standard なら G1 を維持 | Express One Zone は初版の保証の対象外（§15） |
| リージョンやバケットの喪失 | 保証しない | 別途の複製が要る |
| 成功を返せなかったコミット | 残るか消えるかは不定 | 現行と同じ「結果不明」 |

## 3. 全体構成

```text
                 SQL
                  │
 ┌────────────────▼─────────────── primary ───────────────────────────────┐
 │ 実行器 ── MVCC ── Logger ─┬─ ローカル WAL（fsync は独立に進む）              │
 │                           └─ uploader ── 条件付き PUT ×W ──────────────────┼──► wal/<epoch>/<seq>
 │ 行ページ（RAM・blocks）                                                     │
 │ TLCS・LSM ラン・blocks ── 範囲キャッシュ ◄── Range GET ────────────────────┼─── objects/...
 │ checkpointer ── マニフェスト ───────────────────────────────────────────────┼──► checkpoints/...
 └─────────────────────────────────────────────────────────────────────────────┘
        control/writer.json（CAS）、epochs/<n>.json（不変）
 standby ×N：wal/ を順に GET して検証し、コミット単位で適用。objects/ は必要になったときに読む
```

## 4. 位置と用語

LSN は現行どおり WAL のバイト位置で、範囲は半開区間 `[start, end)` とする。

| 用語 | 意味 |
|---|---|
| `BufferedLSN`、`CommittedLSN`、`DurableLSN` | 現行のまま（§1.3） |
| S3 永続化 LSN | その writer のエポックで、連番 1 から欠けなく保存を確認したチャンクの末尾。エポックの開始位置から始まる |
| 応答 LSN（`ReplyLSN`） | 応答の可否の判定に使う位置。S3 同期モードでは S3 永続化 LSN、ローカルモードでは `DurableLSN` |
| 正式な履歴 | 復元が S3 から読む WAL。エポックごとにチャンクの連鎖を起点から辿り、次のエポックの開始位置で切って、つなげたもの |
| 起点 | 連鎖を辿り始める位置。「次に読む連番、そのチャンクが始まるべき LSN、直前のオブジェクトの SHA-256」の組で表す（§9.3）。エポックの連番 1 も起点の一つで、その直前はエポック記録である。どの起点から辿っても、その先の履歴は同じになる |
| エポック | 1 回の writer の起動が書く範囲。キー空間 `wal/<epoch>/` を占有する |
| 封印 | エポックの最初の空き連番に、条件付き作成で置く終端マーカー。消さない |
| 転送 | 再起動または昇格。封印、次のエポックの作成、`writer.json` の切り替えからなる |
| データオブジェクト | TLCS、LSM ラン、blocks の範囲、スナップショット、ページ対応表を S3 に置いたもの |
| マニフェスト | チェックポイントを構成するオブジェクトの一覧と、チェックポイント記述子（§9.1） |
| 有効なマニフェスト | `writer.json` が指すマニフェストから、親を辿って届くもの（§5.5） |
| 確定 | データオブジェクトへの参照が以後増えない状態。作ったエポックの封印か、その writer の宣言による（§13.2） |

## 5. S3 上の配置

### 5.1 キー

キーはすべて `clusters/<cluster-id>/` の下に置く。制御キー、エポック記録、WAL チャンクのヘッダー、マニフェストには、形式の版とクラスタ ID を入れる。データオブジェクトの本文と範囲ダイジェスト表には入れない。クローンで、サーバー側のコピーをそのまま使えるようにするためである（§14）。

| キー | 種類 | 内容 |
|---|---|---|
| `control/writer.json` | 可変（CAS） | 世代番号、状態（`active` / `transfer`）、現行エポック、所有インスタンス、転送中ならその世代番号と候補、最新の有効なマニフェストへの参照 |
| `control/gc.json` | 可変（CAS） | GC の実行権と世代、マークの記録、記録中の削除の集合、読者の登録（§13.4） |
| `epochs/<20桁>.json` | 不変 | 開始 LSN、親エポックと封印の連番・ダイジェスト、作成した転送の世代番号（`tgen`）、候補インスタンス。消さない |
| `wal/<epoch 20桁>/<seq 20桁>` | 不変 | WAL チャンク、または封印。封印は消さない |
| `objects/<epoch 20桁>/<seq 20桁>` | 不変 | データオブジェクト。アップロードのたびに新しいキーを使い、連番はエポックの中で単調に増やす |
| `objects/<epoch>/<seq>.ranges` | 不変 | 範囲ダイジェスト表（§5.4） |
| `checkpoints/<epoch 20桁>/<seq 20桁>.json` | 不変 | チェックポイントのマニフェスト |

不変キーは `PutObject(If-None-Match: *)` で一度だけ作る。可変キーは、`GetObject` で読んだ ETag を `If-Match` に渡して丸ごと置き換える。S3 の条件付き書き込みは PutObject、CompleteMultipartUpload、CopyObject で使え、既存キーへの `If-None-Match` と ETag の不一致は 412 になる（[条件付き書き込み](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)）。全リクエストに `ExpectedBucketOwner` を付ける。

### 5.2 WAL チャンク

ヘッダーには、形式の版、クラスタ、エポック、連番、開始・終了 LSN、直前のオブジェクト（連番 1 ならエポック記録）の SHA-256、WAL の幾何（セグメントの大きさ、レコードの版）、writer のインスタンス ID、作成時刻を入れる。ボディは、元の LSN を復元できる「(LSN, 長さ, バイト列)」の並びにする。セグメント末尾のパディングは並びの隙間で表す。レコードを途中で切らないので、チャンクの最大長 `C_max` は `Logger::kMaxRecordSize` 以上にする。

直前のダイジェストは、切り出しの時点でローカルに計算できる。前のチャンクの保存確認を待つ必要はないので、パイプライン化の妨げにならない。

### 5.3 封印とエポック記録

封印は、エポック、連番、終了 LSN、直前のチャンクのダイジェスト、転送の世代番号（`tgen`）、転送 ID を持つ。封印より後の連番に何が届いても、正式な履歴には入らない。

エポック記録 `epochs/<n>.json` は、開始 LSN（親エポックの封印の終了 LSN）、親エポック、封印の連番とダイジェスト、`tgen`、候補インスタンスを持つ。`tgen` は、より新しい転送とより古い転送を区別するのに使う（§11.2 の T2、T4）。

**封印とエポック記録は、保持期間に関係なく消さない。** 封印を消すと、死んだ writer の遅れた PUT や再送が、その連番に条件付き作成で成功する。その writer は 200 を受けて S3 永続化 LSN を進め、成功を返す。しかし正式な履歴は次のエポックの開始位置でそのエポックを打ち切っているので、そのコミットは無い（§18.1、`s3wal_bug_sealgc`）。残るのはエポックあたり 2 つの小さなオブジェクトで、数は転送の回数に比例するだけである。

### 5.4 データオブジェクト

- **キーはアップロードごとに新しくする。** 内容のハッシュをキーにすると、同じ内容の古いオブジェクトを再利用した直後に、GC がそれを消しうる（§13、§18.3）。連番はエポックの中で単調に増やす。確定の水位（§13.2）がこの順序を使う。
- **WAL の参照は同じエポックのオブジェクトだけを指す。** `kInstallColumnar` などの WAL レコードが指せるのは、そのエポックの writer が作ったオブジェクトに限る。前のエポックのオブジェクトを使い続ける経路は 2 つに限る。1 つは有効なマニフェストからの引き継ぎ、もう 1 つは転送の後の最初のマニフェストへの掲載である。後者は、封印までの正式な WAL を再生して得た状態が参照するオブジェクト（前の writer が最新のマニフェストの後に install したものを含む）を、新しいマニフェストに載せることをいう。そうしたオブジェクトは、新しいマニフェストが有効になって封印の終了を覆うまで確定しないので（§13.2）、それまで消えない。
- オブジェクト全体の SHA-256 に加え、4 MiB ごとの SHA-256 を並べた範囲ダイジェスト表を `.ranges` として保存する。範囲読みのたびに該当範囲を検証できる。参照は「キー、大きさ、SHA-256、範囲ダイジェスト表のキーと SHA-256」の組で持つ。
- 64 MiB を超えるものはマルチパートでアップロードし、`CompleteMultipartUpload` に `If-None-Match: *` を付ける。409 なら最初からやり直す。パートは 5 MiB〜5 GiB、1 回のアップロードで 10,000 個までなので（[マルチパートの上限](https://docs.aws.amazon.com/AmazonS3/latest/userguide/qfacts.html)）、パートの大きさは「64 MiB と、大きさの 1 万分の 1 を 4 MiB の倍数に切り上げたものの大きい方」にする。64 MiB に固定すると、625 GiB が上限になる。単一オブジェクトの上限は 50 TB（[発表](https://aws.amazon.com/about-aws/whats-new/2025/12/amazon-s3-maximum-object-size-50-tb)）。中断したアップロードは、ライフサイクルの `AbortIncompleteMultipartUpload` で片付ける。

### 5.5 マニフェストと writer.json

マニフェストは、クラスタ、エポック、連番、親マニフェストのキーと SHA-256、チェックポイント記述子（§9.1）、WAL の起点（§9.3）、トランザクション ID の上限、スナップショットとデータオブジェクトの参照（役割つき：blocks の世代と範囲、LSM ラン、表ごとの TLCS）、install の一覧（親の被覆上限と自分の再生開始 LSN の小さい方から、自分の被覆上限までの WAL にある `kInstallColumnar` が指すオブジェクト）、実行中のクエリが固定するオブジェクト、確定の水位（§13.2）、WAL の幾何、形式とバイナリの版、作成時刻を持つ。

**マニフェストが有効になるのは、`writer.json` の参照がそれに替わったときである。** 復元・standby・GC は、`writer.json` が指すマニフェストから親を辿って届くものだけを使う。死んだ writer のマニフェストの PUT が遅れて届いても、この連鎖には入らないので使われない。

`writer.json` は、世代番号（CAS ごとに 1 増やす）、状態、現行エポック、所有インスタンス（ホストと起動ごとの ID）、転送中なら `tgen`・候補・開始時刻・隔離の記録、最新の有効なマニフェストの参照を持つ。

## 6. WAL の送信

### 6.1 不変条件

- **U1** チャンクは、自分のエポックのキーにだけ、条件付き作成で書く。
- **U2** S3 永続化 LSN は、連番 1 から欠けなく成功を確認したチャンクの末尾までしか進めない。後ろのチャンクが先に成功しても、前が欠けていれば進めない。
- **U3** 412 を成功とみなさない。`HeadObject(ChecksumMode=ENABLED)` で保存済みの SHA-256 を読み、自分の本文と一致したときだけ成功とする。封印なら送信を止める（以後このエポックには書けない）。別の内容なら止めて警報を出す。
- **U4** 送るのは完結したレコード（`CommittedLSN` 以下）だけ。ローカルの fsync の完了は待たない。
- **U5** S3 永続化 LSN より上のローカル WAL は消さない。それより下は S3 にもあるので、ローカルの WAL はキャッシュとして扱い、容量に応じて古い方から消してよい（§6.4）。
- **U6** エポックは writer の起動ごとに新しくする（§11）。
- **U7** 前のエポックで送れなかった WAL の末尾は、新しいエポックで送らない（§11.2 の T5）。

### 6.2 切り出し

| 条件 | 動作 |
|---|---|
| 送信中の PUT が 0 | 未送信分をすぐ切り出す |
| 未送信分が `c_bw`（既定 1 MiB）以上 | 空きがあれば切り出す |
| 前回の切り出しから `linger`（既定：直近の PUT 所要時間の中央値の半分）が過ぎた | 空きがあれば切り出す |
| 送信中のチャンクが W（既定 8） | 待つ |

1 チャンクは最大 `C_max`（既定 16 MiB）で、それを超える分は複数のチャンクに分ける。コストの上限として、PUT の最大レートも設定できる。

**空きができたらすぐ切り出す方式にしない理由。** 送信中のチャンクはそれぞれが独立したレイテンシの抽選になる。あるコミットは、それより前の全チャンクを待つ。そのため、チャンクを細かく増やすほど中央値が悪化し、PUT の数も増える。さらに W 個の枠が常に埋まるので、ヘッジを送る空きも無くなる。模擬実験（S3 Standard を仮定、毎秒 2,000 コミット）では、即時切り出しが p50 80 ms・p99 237 ms・毎秒 212 PUT、適応型（ヘッジあり）が p50 52 ms・p99 134 ms・毎秒 71 PUT だった。直列（ヘッジなし）は p50 64 ms・毎秒 24 PUT だが、帯域が 1 接続分で頭打ちになる（§16.2）。

### 6.3 ヘッジと再試行

直近の中央値の 3 倍を過ぎても終わらない PUT は、同じキー・同じ本文で 1 度だけ重ねて送り、先に終わった方を採る。後から終わった方は 412 になり、U3 の照合で一致する。ヘッジも接続と帯域を使うので、物理リクエストの数は「チャンクの枠 W ＋ ヘッジ専用の枠（既定 2）」で抑える。ヘッジは元の PUT が終わるまで枠を占め、終わった時点で遅い方を取り消す。

ヘッジが無いと p99 が大きく悪化する（毎秒 2,000 コミットで 134 ms から 448 ms）ので、必須とする。専用の枠は高負荷で効き、毎秒 40,000 コミット（330 MB/s）で p99 を 260 ms から 233 ms に、Express One Zone では 46 ms から 33 ms に下げる（§16.2）。AWS も、レイテンシを安定させるには積極的なタイムアウトと再試行が効くとしている（[性能の指針](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)）。

| 応答 | 処理 |
|---|---|
| 200 | 成功 |
| 412 | U3 で照合 |
| 409（同時の削除との競合） | バックオフして、同じ条件・同じ本文で再送する |
| 5xx、タイムアウト、切断 | 同じ本文で再送する。条件付き作成なので二重にはならない |
| 503 Slow Down | バックオフする。プレフィックスあたり毎秒 3,500 PUT を超えないようにする（[性能の最適化](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)） |
| 403、400 | 設定の異常とみなして送信を止め、警報を出す。応答は待たせる |

SDK の自動再試行の結果はそのまま使わず、必ずこの表を通す。自動再試行の 2 回目が 412 を返すことがあるからである。

### 6.4 ローカル WAL と fsync

アップロードはローカルの fsync と並行に進め、応答は S3 永続化 LSN だけを見る。ローカルの fsync は、ローカルの WAL-before-data と速い再起動のために残す。TLA+ の `s3wal_design_nofsync` は、クラッシュで fsync 済みの WAL まで失われる場合も安全性が保たれることを示した（§18.1）。

S3 永続化 LSN より下のローカル WAL はキャッシュである（U5）。現行は、チェックポイントの再生開始点（`min(スナップショットの LSN, 最古の実行中トランザクションの最初の LSN)`）より下になるまでセグメントを回収しない。そのため長い書き込みトランザクションが古いセグメントを固定し、S3 が正常でもローカルの WAL が増え続ける。S3 同期モードでは、この固定をローカルの容量から外す。

- 再起動の再生で、ローカルに無い範囲は S3 から読む。
- 実行中のトランザクションは、コミットとアボートで自分の WAL を読み返す（`TransactionManager::ReadWalRecordAt`）。ローカルに無ければ、チャンクの一覧（連番と LSN の範囲）から S3 を範囲で読む。
- 読み返しの遅延を避けたい運用のために、1 トランザクションの WAL の量に上限を設定できるようにする。

再起動では、ローカル WAL を正式な履歴に合わせる。ローカルの方が長ければ末尾を捨て、短ければ差を S3 から取り寄せる（§11.2 の T5）。

### 6.5 S3 が遅い・止まったとき

未送信の WAL のバイト数、保留中の応答の数とバイト数、未応答のコミットが固定している MVCC メモリに上限を設ける。上限に達したら、新しい書き込みトランザクションをステートメントのタイムアウトまで待たせ、その後エラーにする。目標の位置が既に応答 LSN 以下の読み取りは、そのまま返す。未送信の WAL は捨てない。ローカルディスクの空きが尽きたら書き込みを止める。

## 7. 応答のバリア

### 7.1 規則

応答が待つ目標 LSN は、次の最大値とする。

1. 自身のコミット終端。S3 同期モードでは、すべてのコミットを同期にする（§2）。
2. D4 の版の依存（現行どおり）。
3. 引いた LSM の木（索引・カタログ）ごとの**公開済み変更 LSN**。カーソルを開いた後、またはキーを引いた後に読む。
4. 追跡していない経路では、読んだ時点の**公開済みコミット LSN**。

結果を含むフレームは、その時点の目標まで応答 LSN が届いてから送る。結果を分割して送る場合は、フレームごとに目標を確かめる。目標は読み進めるにつれて単調に増えるだけなので、新しい木やカーソルに触れない限り、2 つ目以降のフレームは待たずに出る。

### 7.2 値を上げる位置

- **木ごとの値は、LSM への反映より前に上げる。** 現行のコミットは、`ApplyTransactionCommitRecords` で LSM のコミット済みの状態を更新し、続けて `CommitVersions` で版を可視にする。索引のカーソルは版より先に LSM を読みうるので、`CommitVersions` の前に上げるだけでは足りない。変更した木ごとの公開済み変更 LSN と公開済みコミット LSN を、このコミットの終端 LSN へ、`ApplyTransactionCommitRecords` の前に単調に上げる。上げる側は release、読む側は acquire で同期する。順序が逆だと、反映の直後に読んだ側が古い値を見る（§18.2、`barrier_tree_late`）。
- 版チェーンは、最新の `commit_lsn` が応答 LSN 以下になるまで GC しない。早く消すと、ヒープを読んでも依存が残らない（`barrier_version_gc`）。
- 再起動の直後は、木ごとの値を、復元した WAL の末尾にしてよい。T5 でローカル WAL を正式な履歴の末尾に切り詰めるので、その時点の内容はすべて S3 にある（§11.2）。

### 7.3 カーソルとスナップショット

索引のカーソルは、開いた時点の LSM（コミット済みのメモ表、不変のメモ表、ラン）を取り込む（`page/page_manager.cpp`）。そのため、スナップショットの時点の値を 1 度待つだけでは足りない。スナップショットを取った後に DELETE がコミットされ、その後に開いたカーソルがその DELETE の結果を見たとき、スナップショットの時点の値はその DELETE を覆わない。規則 3 と 4 の値は、スナップショットの時点ではなく、カーソルを開いた時点、またはキーを引いた時点に読む。

### 7.4 旧版の `BufferedLSN` を使わない理由

`BufferedLSN` まで待つと、未完了のトランザクションのレコードや、スナップショットの後のコミットまで待つ。§7.1 の目標は、公開済みのコミットの最大 LSN を超えない（Lean の `Barrier.target_within_published`）。書き込みのない表や索引だけを読む文は待たない。書き込み中の索引を引く文は、およそ 1 回のアップロード分を待つ。索引のキーごとに LSN を持たせれば、さらに細かくできる（§22）。

## 8. TLCS 圧縮とデータオブジェクト

### 8.1 圧縮の手順（S3 同期モード）

1. 静止を確認する（現行どおり）。
2. TLCS ファイルをローカルに書く。名前には世代を付ける（§8.3）。
3. データオブジェクトとして、このエポックの新しいキーにアップロードし、範囲ダイジェスト表も保存する。
4. 1 つのトランザクションで、索引の更新（LSM のレコード）、`kInstallColumnar`、`kCommit` を書く。`kInstallColumnar` は、表の `first_pid`、オブジェクトの参照、レイアウトの世代、ページ対応表（旧ページ ID と、スタブのページ ID・行数。大きければその参照、§8.4）を持つ。
5. 公開の時点でチェーンをスタブに差し替え（`PageManager::ReplaceTableChainWithColumnarStubs`）、TLCS を表に結び付ける。

**順序の規則**は「オブジェクトが先、参照が後」で、参照は同じエポックのオブジェクトだけを指す（§5.4）。オブジェクトは確定するまで GC されない（§13.2）。そのため、WAL の参照が正式な履歴に入った時点で、オブジェクトは必ず S3 にある。アップロードの後に送信がどれだけ止まっても変わらない。前版の「アップロードから `RefWindow` 以内に参照を応答 LSN に入れ、間に合わなければ新しいキーで上げ直す」規則は、既にローカル WAL に書いた参照を直せないので廃止した（§18.5）。

### 8.2 再生

`kInstallColumnar` を持つトランザクションのコミットを再生すると、旧ページを解放し、記録どおりのスタブを作り、表をオブジェクトに結び付ける。TLCS の本体は、必要になったときに範囲キャッシュから読む。以後の「スタブのページ ID・行番号」を指す変更は、primary と同じ配置に適用されるので、standby でも復元でも一致する。

**再生は冪等にする。** チェックポイントはファジーなので、再生開始 LSN より後ろの install を既に含みうる。`kInstallColumnar` は表のレイアウトの世代（差し替えの前と後）を持ち、再生は、表の現在の世代が「前」と一致するときだけ旧ページを解放してスタブを作る。一致しなければ（ベースが install の後の状態を含む）何もしない。旧ページ ID が別の用途に割り当て直されていても、世代が一致しない限り触れない。これが成り立つよう、差し替えはチェックポイントの取得と排他にする（表のレイアウトのラッチ）。

### 8.3 効果とローカルモード

- primary で圧縮でき、standby と復元が同じオブジェクトを使う。
- 索引の更新とチェーンの差し替えが 1 つのコミットで原子的になる。
- **ローカルの TLCS の名前に世代を付ける**（`<db>.tlcs.<first_pid>.<世代>`）。現行の名前は `first_pid` ごとに 1 つなので、再圧縮が同じパスを上書きする（`database/database.cpp` の公開の順序）。新しい `kInstallColumnar` のコミットの前に止まると、旧チェックポイントのスタブが指すべき旧ファイルが失われる。旧ファイルは、それを参照するチェックポイントから再生できる間は残す。これで、ローカルモードでも圧縮の直後にチェックポイントを強制する必要がなくなる。S3 同期モードのローカルファイルは、オブジェクトのキーで名付けたキャッシュになる。
- WAL 形式の版を 8 に上げる（ADR 0011。[wal_format.md](wal_format.md) を同じ変更で更新する）。

### 8.4 大きな表

現行の圧縮は表全体を書き直す。DB がローカルディスクを超える規模では、次の 3 つが表の大きさに比例し、そのままでは G4 に届かない。

- **アップロード。** 1 つの表を複数の不変な TLCS セグメントに分け、圧縮は「行ページの差分から新しいセグメントを作る」だけにする。スタブは（セグメント、ブロック）を指す。hydrate で使われなくなったブロックの割合が閾値を超えたセグメントは、併合で作り直す。
- **ページ対応表。** `kInstallColumnar` に旧ページ ID とスタブを全件載せると、WAL の 1 レコードの上限（`Logger::kMaxRecordSize`、16 MiB − 64 KiB）を超えうる。大きな対応表は不変のデータオブジェクトとして置き、レコードはその参照だけを持つ。再生とメモリの負担を抑えるため、1 回の install が置き換えるページ数にも上限を設け、大きな表は複数の install に分ける。
- **索引の更新。** 現行の索引の作り直しは、全キーを `std::map` に集める（`database/database.cpp`）。セグメント単位の install では、置き換えた行の位置だけを索引で更新する。

形式は別の ADR で決める。

## 9. チェックポイント（S3 上のベース）

### 9.1 チェックポイント記述子

現行の `WriteCheckpoint()` は、再生開始 LSN（`min(スナップショットの LSN, 最古の実行中トランザクションの最初の LSN)`、`recovery/checkpoint_manager.cpp`）だけを返す。スナップショットの出力は開始の後も続き、開始時点より新しいコミットを取り込む。そのため現行の実装は、公開の直前に、反映したコミットの耐久化を待ち直している（`page/page_manager.cpp` の `WaitForDurableLSN(ReflectedCommitDurableTarget())`）。S3 に置くには、チェックポイントの生成が次の記述子を返すようにする。

- **再生開始 LSN**：現行の戻り値。コミットの無いレコード（アボートや未完了のトランザクション）だけでも、被覆上限より先に進みうる。
- **被覆上限 LSN**：スナップショットが反映したコミットの終端の上界。スナップショットは、これより後ろのコミットの効果を含まない。開始時の LSN や `BufferedLSN` では代えられない。現行の `ReflectedCommitDurableTarget()` は、通常のコミットの反映では上がるが、ベースを読み込むと再生開始 LSN に戻され（`page/page_manager.cpp` の `max_reflected_commit_end_`）、WAL の再生では上がらない。そのため、再起動の直後に取ったチェックポイントでは上界にならない。ベースの被覆上限をスナップショットに保存して読み込み時に戻し、再生が終わったら実際に再生した WAL の末尾まで上げる。それまではチェックポイントを取らない。
- **固定した世代**：スナップショットが参照する `.db`、LSM ラン、blocks、TLCS の世代。アップロードが終わるまで、次のチェックポイントや再圧縮がそれらを消したり差し替えたりしないよう固定する。

### 9.2 手順

1. ローカルのチェックポイントを書き、記述子を得る。S3 同期モードでは、ローカルのチェックポイントの公開（rename）も、応答 LSN が被覆上限と再生開始 LSN の大きい方以上になってから行う。こうしておくと、T5 でローカル WAL を正式な履歴の末尾に切り詰めても、ローカルのチェックポイントがそのまま使える（§11.2）。
2. 固定した世代のファイルのうち、まだ S3 に無いものをデータオブジェクトとしてアップロードする。blocks は追記型なので、追記された範囲だけを送る。
3. S3 永続化 LSN が、被覆上限と再生開始 LSN の大きい方以上になるのを待つ（S3 での WAL-before-data）。再生開始 LSN が正式な履歴の末尾を超えたベースから復元すると、新しい writer はその手前から書き始め、そのコミットは次の再生で読み飛ばされる。
4. マニフェストを条件付き作成で置く。
5. 自分がまだ `active` の所有者なら、`writer.json` のマニフェスト参照を CAS で更新する。これでマニフェストが有効になる（§5.5）。CAS が失敗したら、このマニフェストは使われない。
6. 世代の固定を解く。

書き込みは止めない。復元にかかる時間は「スナップショットの取得＋再生開始 LSN からの再生」で決まるので、前回からの WAL が 1 GiB を超えたか 10 分が過ぎたときに取る。

**ローカル形式への要求。** `<db>.lsm.<gen>` は、チェックポイントのたびに全体を書き直すので、毎回すべての索引をアップロードすることになる。差分にするには、LSM のランを 1 つずつ不変オブジェクトにする。スナップショット `<db>.db` はページ数に比例するので、DB が大きい場合は ADR 0009 の段階 2（ディレクトリの永続化）で差分にする。初版は丸ごとアップロードし、規模の試験で必要になった時点で差分化する。

### 9.3 WAL の起点

マニフェストには次の 2 つの位置を記録する。位置は「エポック、次に読む連番、そのチャンクが始まるべき LSN、直前のオブジェクト（連番 1 ならエポック記録）の SHA-256」の組で表す。この表し方なら、まだチャンクが無い位置（空のエポックや、書き込みの止まった DB の最初の導入）も表せる。

- **復元の起点**：再生開始 LSN を含むチャンク。再生開始 LSN がチャンクの境界にあれば、その次の連番。復元はここから連鎖を辿り、これより前のチャンクを読まない。
- **走査の起点**：マニフェストを置く時点で確認済みの、連続した接頭部の次の連番。転送の封印（T3）は、そのエポックの最新の有効なマニフェストの走査の起点から辿る（無ければ連番 1 から）。standby を昇格するときは、standby が検証済みの位置の方が新しければ、そこから辿る。

どちらも、保存済みの連続した接頭部の中にある。Lean の `Origin.walk_from_origin` は、連番 1 から辿った履歴が「起点までの連鎖」と「起点から辿った履歴」をつないだものに等しいことを示す。`Origin.walk_ignores_below` は、起点から辿る走査が起点より下のキーを読まないことを示す。したがって、起点より下の WAL を消しても、起点から辿る正式な履歴は変わらない。連番 1 から辿る定義のままでは、毎秒 70 チャンクなら 1 日に約 605 万オブジェクトを走査し直すことになり、昇格が遅くなる。

### 9.4 最初の導入

新しいローカルチェックポイントの再生開始 LSN をエポック 1 の開始にし、そこからの WAL をエポック 1 としてアップロードする。続けてチェックポイントを置き、S3 永続化 LSN が追いついたら同期モードに切り替える。それまでの応答は、ローカルモードの基準で返す。

## 10. 範囲キャッシュとローカル容量を超える DB

### 10.1 ローカルに必ず置くもの

| 種類 | 理由 |
|---|---|
| 未送信の WAL | S3 永続化 LSN より上はローカルにしかない |
| 未アップロードのファイル | 書き戻し中。参照はアップロードの後にしか作らない |
| スピル（[ADR 0005](adr/0005-spill-store-placement.md)、[ADR 0007](adr/0007-uncommitted-pages-private-spill.md)） | 未コミットの状態と作業データ。S3 には置かない |
| メモリ上の行ページ | 変更の差分。退避先の blocks は範囲キャッシュに載る |

TLCS、LSM ラン、blocks の範囲、スナップショットは、アップロードが済めばローカルから追い出してよい。

### 10.2 キャッシュ

- 単位は、オブジェクトの 4 MiB に揃えた範囲。マルチパートのパート境界をまたがない。AWS は、マルチパートのオブジェクトをパート境界に揃えて読むよう勧めている（[性能の指針](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance-guidelines.html)）。
- 容量はバイト数で数え、追い出しは現行と同じ FIFO＋参照ビットで始める（[ADR 0010](adr/0010-resident-pages-by-bytes.md)）。大きな走査がキャッシュを流さないよう、1 度しか触れていない範囲は先に追い出す。
- 実行中のクエリが使う範囲は参照数で固定する。
- オブジェクトは不変で、キーは使い回さない。そのためキャッシュの中身は再起動の後もそのまま使え、読み込むときに範囲ダイジェストで検証すれば足りる。

### 10.3 読み取りの経路

TLCS の pread の経路（`PreadAllFd`）を、オブジェクトファイルの `Pread` に置き換える。キャッシュに無い範囲はまとめて Range GET する。ディレクトリグループとゾーンマップを含むメタディレクトリは常駐させ、刈り込みに GET が要らないようにする。順に走査するときは、先のディレクトリグループを 16〜64 本の並行 GET で先読みする。AWS は、同じオブジェクトの別範囲を並行に読むと総帯域が上がり、1 インスタンスで最大 100 Gb/s に届くとしている（[性能の最適化](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)）。mmap の常駐モードは、ファイル全体がキャッシュにあって固定できるときだけ使う。

### 10.4 性能の見込み

キャッシュが温まっていれば、ローカルファイルを読む場合と同じである。冷えた走査は、並行 GET の総帯域で律速される。小さいオブジェクトの初回応答は概ね 100〜200 ms とされる（[性能の最適化](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)）ので、行ページの退避先が冷えていると、点検索のたびにその遅延が乗る。OLTP の作業集合はローカルに収まる大きさにする。

### 10.5 規模の上限

非常駐ページの記述子は、ページ数に比例して RAM に残る（ADR 0009 段階 1）。TLCS のディレクトリグループのメタと LSM ランのメタも、データ量に比例する。ローカルディスクを大きく超える規模では、ディスクより先に RAM が上限になる。目標の規模（例：最小メモリ 1 GB で 1 TB）を満たすには、ADR 0009 の段階 2 が前提になる。

### 10.6 ローカルディスクの見積もり

ローカルディスク ≥ 未送信 WAL の上限 ＋ 送信済み WAL のキャッシュの上限 ＋ アップロード待ちのファイル（固定した世代を含む） ＋ スピルの上限 ＋ キャッシュの下限（作業集合）。DB 本体の大きさは入らない。

送信済みの WAL は、長い書き込みトランザクションが再生開始点を固定していても、キャッシュの上限を超えた分を消してよい（U5、§6.4）。未送信 WAL は S3 の停止中に増えるので、§6.5 の上限で書き込みを絞る。

## 11. エポック：再起動と昇格

### 11.1 状態

```text
active(e, I) ──T1──► transfer(tgen=g, 候補 J) ──T6──► active(e', J)
                          │  T1 で別の候補が上書きできる（世代番号が増える）
```

### 11.2 転送の手順

- **T1** 運用者（または監視役）が `writer.json` を CAS で `transfer` にし、世代番号を `g` に上げ、候補を記す。同じホストで再起動する場合は、先に旧プロセスを止める。
- **T2** 候補は、存在するエポック記録のうち最大の `n` を求め、その記録の `tgen` を確かめる。`tgen` が `g` より大きければ、自分は追い越されているので手を引く。
- **T3** エポック `n` を封印する。走査の起点（§9.3）から、各チャンクが前の終わりから始まることを確かめながら辿る。最初の空き連番に、封印を条件付き作成で置く。412 なら、そこに届いた内容を読み直して続きを辿る。既に封印があれば、それを使う。旧 writer が書き続けると、空きの連番を先に取られ続けて封印を置けないことがある。安全性には響かないが、昇格が終わらない。412 が続いて走査が進まないときは、旧 writer の隔離を確かめるか、旧 writer のリースが切れる（L＋δ）のを待ってから続ける。writer は、`writer.json` のリースの延長に失敗したら、新しいチャンクを切り出さない（§11.3）。
- **T4** `epochs/<n+1>.json` を条件付き作成で置く。開始 LSN は封印の終了 LSN、`tgen` は `g` とする。既にあれば、その `tgen` を比べる。自分より古い転送のものなら、そのエポックを T3 で封印して `n+2` へ進む。自分より新しい転送のものなら、手を引く。
- **T5** ローカルの状態を、正式な履歴 H（封印の終了まで）に合わせる。
  - ローカルのチェックポイントの被覆上限と再生開始 LSN がどちらも H の末尾以下で、再生開始 LSN から H の末尾までの WAL がローカルか S3 に欠けなくあり、ローカル WAL が重なる範囲で H と一致していれば（チャンクごとの SHA-256 を比べる）、ローカル WAL を H の末尾で切り詰めて使う。H の方が長ければ、差を S3 から取り寄せる。再生開始 LSN を確かめないと、H の末尾より先を再生開始とするベースのまま開いてしまう。その後に H の末尾から書いたコミットは成功を返すが、次の再起動の再生で読み飛ばされて消える（現行のストレージで再現した）。
  - そうでなければ、ローカルの WAL とデータファイルを捨て、有効なマニフェストと WAL から復元する。
  - **H より後ろのローカル WAL は使わない。** その末尾を新しいエポックで送ると、2 つの保証が崩れる。1 つは再起動直後の読み取りで、SQL を開いた時点の状態に S3 に無いコミットが含まれ、版チェーンの無い行をヒープから読む経路はその依存を記録しない（`s3wal_bug_tail`）。もう 1 つは GC で、封印で捨てられたはずの参照が後のエポックで正式になり、消したオブジェクトを指しうる（`objgc_bug_tail`）。末尾のコミットは成功を返していないので、捨てても G1 に反しない。
- **T6** `writer.json` を CAS で、世代番号が `g` のままなら `active(n+1, 自分)` にする。失敗したら手を引く。SQL を開くのは、旧 writer の隔離（§11.3）を確認した後である。

T2 と T4 の `tgen` の確認は、TLA+ で見つけた穴を塞ぐためのものである。T1 と T2 の間に別の転送が追い越してエポックを作りうるので、T2 で確かめないと、T1 の直後に止まった候補が、追い越した転送のエポックを最初の封印の対象に選んでしまう（`s3wal_bug_t2race`）。T4 で比べずに後続のエポックを封印すると、追い越された古い候補が新しい転送のエポックを封印してしまう（`s3wal_bug_chase`）。どちらも、`active` の writer が 1 件も書けなくなる。T5 の一致の確認を省くと、古いホストの WAL が正式な履歴と食い違ったまま再開する（`s3wal_bug_reuse`）。

### 11.3 隔離（読み取りの最新性）

封印の後、ゾンビは新しいコミットに成功を返せない。ゾンビの PUT は封印の連番で 412 になり、連続した接頭部を延ばせないからである。それでも、古い状態の読み取りは返しうる。primary に向ける接続に最新の結果を保証するには、次のどちらかを使う。

- **隔離** 同じホストではプロセスを止める。別のホストでは、旧ホストの電源断かネットワーク遮断を確認し、`writer.json` に記録してから T6 で SQL を開く。
- **リース** writer は `writer.json` のリース期限を周期的に CAS で延ばす。延長が成功したら、その要求を出す直前の単調時計から L の間だけ所有するとみなし、期限を過ぎたら読み取りも止める。候補は、最後に観測したリースから L＋δ を待ってから SQL を開く。必要なのは時計の進み方の誤差に上限があることで、時計の同期は要らない。2 秒ごとに延ばすと、月に約 130 万 PUT（S3 Standard で約 6.5 USD）になる。

### 11.4 再試行と競合

- 候補が途中で止まったら、運用者が T1 からやり直す。既に作られたエポック記録や封印は、そのまま次の転送が使う（T3、T4）。封印とエポック記録は消さないので、何度やり直しても同じものが見つかる。
- 2 人の運用者が同時に転送を始めても、`writer.json` の CAS で順序が決まる。後の転送が先の転送を追い越し、追い越された候補は T2、T4、T6 のいずれかで手を引く。
- 正式な履歴の連鎖が切れている（直前のダイジェストや開始 LSN が合わない）、制御キーが読めない、隔離を確認できない、のいずれかなら新しい writer を開かない。

## 12. Standby

- `writer.json` とエポック記録で追う対象を決め、有効なマニフェストの起点から、チャンクを連番順に先読みしながら GET して連鎖を検証する。封印に達したら、次のエポック記録の親の封印と照合して進む。
- トランザクションのレコードは `kCommit` が届くまで溜め、コミットごとに MVCC の公開として原子的に適用する。大きなトランザクションは、ローカルに持つ WAL の写しから読み直す。読み取りのスナップショットは、最後に適用したコミットにする。
- standby が適用するのは正式な履歴の接頭部だけである。正式な履歴は伸びるだけなので（Lean の `History.walk_monotone`）、適用済みの部分が後で覆ることはない。standby の応答にバリアは要らない。
- データオブジェクトは primary と共有し、範囲キャッシュで読む。standby は圧縮しない。行の配置が primary とずれるからである。
- standby は、再生区間（追従を始めたマニフェストから先）と、実行中のクエリが使うオブジェクトを GC に登録する（§13.4）。適用が進んだら、登録の始まりを新しいマニフェストに進める。登録が切れたら、最新の有効なマニフェストから作り直す。
- 新しいチャンクの検知は GET のポーリングで行い、イベント通知は起こす合図に使う。毎秒 20 回のポーリングは月に約 5,200 万 GET（S3 Standard で約 21 USD）である。
- 昇格は、この standby を候補にした転送（§11.2）である。standby は検証済みの位置（エポック、連番、SHA-256）を持つので、T3 の走査はそこから始め、残りのチャンクを取り込むだけで済む。
- 読んだ直後の書き込みを standby で見たい接続には、primary が返すコミット LSN を渡し、standby はその位置まで適用してから答える（任意の機能）。

## 13. 保持と GC

### 13.1 根

マークの時点で、次のものから届くデータオブジェクトとマニフェストを「到達できる」とする。

- 保持期間内の有効なマニフェスト（§5.5）。参照、固定、install の一覧のすべてを含む。install の一覧を含めるのは、2 つのチェックポイントの間で作られて置き換えられたオブジェクトも、そのマニフェストから再生する PITR で要るからである。
- `writer.json` が指すマニフェスト。
- 保持期間の左端より前で、最も新しい有効なマニフェスト。左端の時点への PITR の起点になる。
- GC に登録された読者の再生区間（§13.4）。登録したマニフェストから最新の有効なマニフェストまでの連鎖上のマニフェストすべてを、参照・固定・install の一覧ごと含む。

保持するマニフェストは、いつも連鎖の末尾側の連続した範囲になる（保持期間、左端の 1 つ、登録の区間のどれも、ある位置から最新までを残す）。そのため、残ったマニフェストの有効性は、`writer.json` から親を辿って確かめられる。

GC は WAL を読まない。最新の有効なマニフェストの被覆上限より後ろの WAL にある参照は根に含めないが、そこから参照されうるオブジェクトはまだ確定していないので消されない（§13.2）。

### 13.2 確定

データオブジェクトを消せるのは、**マークの時点で確定済み**のものだけである。確定済みとは、次のどちらかを満たすことをいう。

- **作ったエポックが封印済みで、有効なマニフェストの被覆上限がその封印の終了 LSN に達している。** 封印より後ろに届いたチャンクは正式な履歴に入らず、未送信の末尾は次のエポックで送らない（U7）。WAL の参照は同じエポックのオブジェクトしか指さない（§5.4）。したがって、そのエポックのオブジェクトへの正式な WAL の参照はすべて被覆上限以下にあって install の一覧に載り、以後は引き継ぎを除いて参照が増えない。
- **作ったエポックの writer が、有効なマニフェストで確定の水位 `q` を宣言している。** 水位は「このエポックの連番 `q` 未満のオブジェクトは、正式でない参照（このマニフェストの被覆上限より後ろの WAL や、まだ有効でないマニフェストからの参照）を持たず、以後新しく参照するのは有効なマニフェストからの引き継ぎだけである」という宣言である。writer は、アップロードを始めたもののうち、この条件を満たさない最小の連番を水位にする。水位があるので、何か月も続くエポックでも、置き換えられたオブジェクトや失敗した圧縮の残骸を、次の転送を待たずに消せる。

確定はマークの時点の値で判断する。スイープの時点の値で判断すると、マークの後に正式になった参照の先を消しうる（`objgc_bug_late_seal`）。参照が未送信のまま確定を宣言すると、送信の後で参照先が消える（`objgc_bug_settle_early`）。

### 13.3 削除の規則

- **データオブジェクト**：マークの時点で到達できず、確定済みのもの。時計は使わない。そのため、アップロードの後に送信がどれだけ止まっても、未確定のオブジェクトは消えない。前版の「作成時刻が猶予期間 `Grace` より古ければ消す」規則では、送信の停止が `Grace` を超えると、遅れて正式になった参照が消えたオブジェクトを指す。同じ内容を新しいキーに置き直しても、WAL の参照は古いキーを指したままなので直せない（`objgc_bug_timebased`）。
- **WAL**：保持する最も古い有効なマニフェスト（左端より前の 1 つと、登録された再生区間の始まりを含む）の、復元の起点より下のチャンク。封印とエポック記録は消さない（§5.3）。起点より下を消しても、起点から辿る履歴は変わらない（§9.3）。
- **マニフェスト**：§13.1 の根に含まれないもの。有効な連鎖に入らなかったマニフェストは、作ったエポックの封印の後に消す。
- GC は `control/gc.json` の CAS で 1 つだけ走らせる。`DeleteObject` には ETag の `If-Match` を付ける（[汎用バケットの条件付き削除](https://aws.amazon.com/about-aws/whats-new/2025/09/amazon-s3-conditional-deletes-s3-general-purpose-buckets)）。

### 13.4 読者の登録と削除の記録

standby、復元、primary の外で長く走るクエリは、再生区間を `control/gc.json` に登録して守る。再生区間は「マニフェスト M から先を再生する」ことを表し、M から最新の有効なマニフェストまでの連鎖と、M の復元の起点から先の WAL を根に加える（§13.1、§13.3）。M だけを守ると、M の後に install されて置き換えられたオブジェクトが消え、追従の途中で読めなくなる。

削除と登録の競合は、時計の同期に頼らず、削除する集合の記録で防ぐ。GC の実行権も `gc.json` の CAS で持ち、引き継ぐときは世代を上げる。古い GC は新しい集合を記録できない。

- 登録と延長は、いつでも `gc.json` への CAS で書ける。
- GC は、マークの結果から削除の候補を求め、その時点の登録の根を除いた集合を、`gc.json`（大きければそれが指す不変オブジェクト）に CAS で記録してから削除を送る。記録した集合の外には削除を送らない。CAS が失敗したら、新しい登録を読み直して集合を求め直す。
- 読者は、登録の CAS が成功したら、依存するオブジェクトが記録中の集合に無く、実際にあることを確かめる。集合にあるものは無いものとして扱い、新しい有効なマニフェストから作り直す。登録より後に記録される集合は、CAS の順序により、その登録の根を除いている。
- 集合は、全件の削除を確かめてから空にする。GC が止まったら、引き継いだ GC が記録中の集合の削除を終えてから次のマークを始める。結果の分からない DELETE が後から届いても、消すのは記録した集合の中だけである。オブジェクトは不変で ETag も変わらないので、`If-Match` はこの遅れた削除を止められない。
- 登録にはリースを付け、読者が周期的に延ばす。読者は、延長の要求を出す直前の単調時計から期間 L の間だけ登録に頼る。GC は、同じ登録が L＋δ の間延ばされないことを自分の単調時計で確かめてから消す（§11.3 と同じ考え方）。
- primary で実行中のクエリが使う古いオブジェクトは、writer が次のマニフェストの「固定」に載せて引き継ぐ。

## 14. PITR とクローン

- 「エポック、コミット終端 LSN」を指定し、有効なマニフェストのうち、被覆上限がそれ以下の最新のものから復元する。両方の再生パスを指定位置で止め、未完了のトランザクションは適用しない。被覆上限はスナップショットが反映したコミットの上界である（§9.1）。再生開始 LSN で代えると、指定位置より後ろのコミットを含むベースを選びうる。
- 時刻での指定は、チャンクのヘッダーの作成時刻でおおよその位置を決め、精密にするには `kCommit` にコミット時刻を入れる（WAL の版 8 で検討）。
- **クローン**：指定位置まで復元し、その状態を新しいクラスタ ID の下で最初の導入（§9.4）として始める。制御キー、エポック記録、WAL チャンク、マニフェストは、新しいクラスタ ID で作り直す。データオブジェクトの本文はクラスタ ID を持たないので、ベースが参照するもののうちローカルに無いものは、元のクラスタからサーバー側のコピーで新しいキーに写す。5 GB までは `CopyObject`（`If-None-Match: *`）、それより大きいものはマルチパートの `UploadPartCopy` で写し、`CompleteMultipartUpload` に `If-None-Match: *` を付ける（[CopyObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CopyObject.html)）。範囲ダイジェスト表も同じく写す。ただし、宛先のバケットポリシーで条件付き書き込みを強制していると、コピーは条件なしなら 403、条件付きなら 501 で失敗する（[条件の強制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html)）。§15 のポリシーを使う宛先では、元のオブジェクトを GET し、条件付きの PutObject（大きければマルチパート）で書く。どちらの経路を使うかは、本番と同じポリシーでの実機試験で決める（P8）。新しいクラスタの保持は、元のクラスタに依存しない。

## 15. 権限と設定

| 役割 | 許可 |
|---|---|
| writer | `wal/`、`objects/`、`checkpoints/` への条件付き作成、`control/writer.json` の CAS、読み取り全般。削除は不可 |
| 転送（運用者） | writer の権限に加え、`epochs/` の作成 |
| standby・復元 | 読み取りと、`control/gc.json` への登録の CAS |
| GC | `DeleteObject` と `control/gc.json` の CAS。封印とエポック記録は消さない |

- バケットポリシーで、不変キーの書き込みに `If-None-Match` を、可変キーの書き込みに `If-None-Match` か `If-Match` を必須にする（[条件の強制](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes-enforce.html)）。不変キーには、ライフサイクルによる失効を設定しない。
- バージョニングを有効にすると、削除マーカーの上に `If-None-Match` で作り直せてしまう。キーを使い回さないことは、削除権限の制限で担保する。封印は WAL と同じプレフィックスにあって権限では区別できないので、GC の実装で除外し、受け入れ試験で確かめる。
- **保存先の選択。** 初版の保証の対象は S3 Standard（汎用バケット）とする。

| 保存先 | PUT 単価（1,000 件、us-east-1） | 保管単価（GB・月） | 遅延 | AZ 障害 |
|---|---|---|---|---|
| S3 Standard | 0.005 USD | 0.023 USD | 小さいオブジェクトで概ね 100〜200 ms とされる | 耐える |
| S3 Express One Zone | 0.00113 USD（加えて 1 GB あたり 0.0032 USD） | 0.11 USD | 1 桁 ms | 耐えない |

  Express One Zone の単価は 2025 年 4 月の値下げ後のもの（[発表](https://aws.amazon.com/blogs/aws/up-to-85-price-reductions-for-amazon-s3-express-one-zone)）。Express One Zone のディレクトリバケットは、アクセス制御の境界がバケット単位で、プレフィックスやオブジェクトのタグでは分けられない。オブジェクトの操作は `CreateSession` のセッションで認可され、書き込みに要る `ReadWrite` のセッションは削除も許す（[認証と認可](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-express-authenticating-authorizing.html)）。そのため、上の表の「writer は削除できない」を実現できず、封印の保護も実装に頼ることになる。Express を保証の対象に入れるかは §22 で決める。条件付き書き込み自体はディレクトリバケットでも使える（[If-Match の発表](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes)）。S3 互換のストレージを使う場合は、条件付き書き込みと読み直しの一貫性を受け入れ試験で確かめる。

## 16. 性能とコスト

### 16.1 帯域とチャンクの大きさ（Lean で証明）

PUT 1 回の所要時間を `a + C/b`（a：固定の遅延、b：1 接続の帯域、C：チャンクの大きさ）とする。

- 持続できる WAL の量 λ は `W·b` 未満である（`Pipeline.capacity_below_bandwidth`）。逆に `λ < W·b` なら、十分に大きいチャンクを選べば支えられ、そのとき a は必要なチャンクの大きさを変えるだけである（`Pipeline.eager_capacity`）。
- ただし実装はチャンクの上限 `C_max` を固定するので、処理量の上限は `W·C_max / (a + C_max/b)` になり、a に依存する（`Pipeline.bounded_chunk_capacity`）。
- 帯域の割合 p/q に届くには `C ≥ p/(q−p)·a·b` が必要十分である（`Pipeline.chunk_sizing`）。b = 80 MB/s、16 MiB のチャンクなら、a = 30 ms で 1 接続の約 87%、a = 100 ms で約 68% になる。
- 直列で上限 `C_max` のチャンクを送る方式は、`C_max / a` を超えない（`Pipeline.serial_bounded_is_latency_bound`）。

そこで G2 は「想定する遅延分布のもとで、物理リクエストを W＋ヘッジ枠に抑えたまま、目標の WAL 量を持続できること」と定め、P0 の実測で確かめる。遅延の裾が重い環境では、W か `C_max` を上げる。

## 17. 障害シナリオ

| 事象 | 振る舞い |
|---|---|
| PUT の結果が不明 | 同じ本文で再送し、412 は照合する（U3） |
| 後ろのチャンクだけ成功 | S3 永続化 LSN は進めない（U2） |
| primary のクラッシュ（ディスク残存） | 同じホストで転送。ローカル WAL を正式な履歴の末尾で切り詰めて使う。未送信の末尾は捨てる（成功を返していない） |
| primary のディスク喪失 | 別のホストで転送し、有効なマニフェストと WAL から復元 |
| 死んだ writer の PUT が遅れて届く | 封印より前なら正式な履歴に入り（連続していれば）、後なら無視される。封印は消さないので、いつ届いても同じ |
| ゾンビ writer | 封印の位置で 412 になり、送信を止める。読み取りは §11.3 で防ぐ |
| 候補が転送の途中で停止 | 運用者が T1 からやり直す。作成済みのエポック記録と封印を引き継ぐ |
| 追い越された古い候補 | T2 か T4 の `tgen` の確認で手を引く。T6 の CAS も失敗する |
| 圧縮中のアップロード失敗 | 参照を作らないので影響なし。残ったオブジェクトは、確定の後に GC が消す |
| 送信が長く止まった後の再開 | 未確定のオブジェクトは消えていないので、遅れて正式になった参照も解決する |
| チェックポイントのアップロード中断 | マニフェストを置かないか、置いても有効にならないので影響なし |
| 遅れて届いたマニフェスト | 有効な連鎖に入らないので使われない |
| standby が保持期間より遅れる | 登録が切れていれば、最新の有効なマニフェストから作り直す |
| 長い書き込みトランザクション | 送信済みの WAL はローカルから消してよい。読み返しは S3 から行う（§6.4） |
| オブジェクトの破損 | 範囲ダイジェストの検証で検出し、別の範囲の取り直しで回復しなければ停止 |
| S3 の長い停止 | §6.5 の上限で書き込みを絞る |
| 連鎖の破れ（ダイジェスト・LSN の不一致） | 新しい writer を開かず、運用者の判断を待つ |
| 再生開始 LSN が正式な履歴の末尾を超えたローカルのベース | 使わずに、有効なマニフェストと WAL から復元する（T5） |
| T3 の走査が、書き続ける旧 writer に追いつかない | 旧 writer の隔離かリースの失効を確かめてから続ける（T3） |
| 結果の分からない DELETE を残して GC が停止 | 引き継いだ GC が、記録中の集合の削除を終えてから再開する。読者は集合にあるものを使わない（§13.4） |
| 削除マーカーによる不変キーの再作成 | 削除権限を与えないことで防ぐ。検出したら停止 |

## 18. 形式検証と模擬実験

TLA+ のモデルは [`tlaplus/`](../tlaplus/)、Lean の証明は [`lean/TinylambOpt/ResearchProofs/S3Durability/`](../lean/TinylambOpt/ResearchProofs/S3Durability/)、模擬実験は [`scripts/primary_s3_upload_sim.py`](../scripts/primary_s3_upload_sim.py) にある。各モデルは、設計の規則を 1 つずつ外した版も持つ。外した版が狙った不変条件で落ちることを確かめるためである。

### 18.1 `S3Wal.tla`：送信・エポック・転送

対象は、パイプライン化した条件付き PUT（任意の順で着き、送り主の死後にも着き、応答は失われうる）、連続した接頭部での応答、エポックの封印と作成、追い越し、ゾンビ、同じホストでの再起動、S3 チェックポイントである。転送は T1〜T6 を別々の操作にしてあり（`BeginTransfer`、`PickTarget`、`ScanStep`、`CreateEpoch`、`Prepare`、`Activate`）、その間に他のホストの操作が割り込む。`Cut` は任意の時点・任意の範囲を切り出せるので、§6.2 の適応型の切り出しと §6.3 のヘッジは、モデルの振る舞いに含まれる。

| 不変条件 | 意味 |
|---|---|
| `NoLostAck` | 成功を返したレコードは正式な履歴にある |
| `DurableIsOfficial` | 生きている writer が耐久化済みとみなす部分は正式な履歴の接頭部 |

`s3wal_design` の状態数が前版（5,688,530）から減ったのは、T5 で末尾を使わなくなり、転送の後のローカル状態が正式な履歴だけで決まるようになったからである。`t2race` は 1 レコード、`sealgc` と `tail` は 2 レコードの小さな設定で反例を出す（`sealgc` は狙いの `NoLostAck` だけを検査する）。

反例の例を挙げる。

- `same_epoch`：ホスト A の writer がチャンクを送っている最中に B へ転送し、B が同じエポックの連番 1 から書き始める。A の要求が後から着いて連番 1 を占め、B のローカル WAL は正式な履歴と食い違う。
- `noseal`：走査で空きと判断した連番に A の遅れたチャンクが着き、次のエポックの開始位置で切ると正式な履歴が縮む。
- `sealgc`：A のチャンクが遅れ、B がその連番に封印を置いて昇格する。封印を消すと、A の再送がそのキーに作成でき、A は 200 を受けて成功を返す。正式な履歴は封印の位置で A のエポックを打ち切っているので、そのコミットは無い。
- `t2race`：A が T1 の直後に止まり、B が追い越してエポック 2 を作り `active` になる。A が再開して T2 で最大のエポック 2 を選び、封印する。B は封印済みのエポックで `active` のまま、1 件も書けない。
- `tail`：A が未送信のコミットをローカルに持ったまま止まり、同じホストで再起動する。末尾を使うと、SQL を開いた時点の状態に S3 に無いコミットが含まれる。

### 18.2 `ReplyBarrier.tla`：応答のバリア

コミットは 1 つのキーを挿入・削除し、耐久化の前に可視になる。読み手はヒープか索引から観測し、規則に従って待ってから応答する。不変条件 `ObservedDurable` は「応答が見せた最新のコミットは、応答の時点で耐久化済み」である。

|---|---|---|
| `barrier_version` | 現行の D4（索引あり） | 違反（索引で 0 件を返す経路） |
| `barrier_version_heap` | 現行の D4（ヒープのみ） | 通過（43,037 状態） |

### 18.3 `ObjectGc.tla`・`GcRegistry.tla`：データオブジェクトと GC

対象は、オブジェクトのアップロード、ローカル WAL への参照の追記、参照を含むチャンクの到着（封印の前ならいつでも、送り主の死後にも）、封印による未送信の参照の破棄、writer による確定の宣言、根からの離脱、マークとスイープである。時計は無く、送信がどれだけ止まるかに上限を置かない。不変条件 `RefsResolve` は「正式な参照の先はすべて存在する」である。

| 設定 | 外した規則 | 結果 |
|---|---|---|
| `objgc_design`（キー 2、エポック 3） | なし | 通過（6,398 状態、深さ 17） |
| `objgc_bug_timebased` | 確定を待たない（到達できなければ消す。猶予期間を超えた停止と同じ） | `RefsResolve` 違反 |
| `objgc_bug_tail` | U7（封印したエポックの未送信の参照を後で送る） | `RefsResolve` 違反 |
| `objgc_bug_late_seal` | 確定をマークの時点で判断する | `RefsResolve` 違反 |
| `objgc_bug_dedupe` | アップロードごとの新しいキー | `RefsResolve` 違反 |
| `objgc_bug_settle_early` | 参照が未送信のものを確定しない | `RefsResolve` 違反 |

`objgc_design` では、封印前のエポックのオブジェクトが確定の宣言を経て消される状態にも到達する（別の検査で確かめた）。規則が厳しすぎて何も消さない、ということはない。

`GcRegistry.tla` は、読者の登録と GC の削除の競合を扱う（§13.4）。読者は登録の後に、記録中の集合に無いことと存在を確かめてから読む。GC はマーク、集合の記録、削除の送信を行う。削除はいつでも（GC の死後にも）届き、別の GC が引き継げる。不変条件 `HeldExists` は「読者が確かめて読んでいるオブジェクトは存在する」である。

| 設定 | 外した規則 | 結果 |
|---|---|---|
| `gcreg_design`（キー 2、GC の停止 2 回） | なし | 通過（1,278 状態、深さ 20） |
| `gcreg_bug_norecord` | 削除する集合の記録（GC のメモリにだけ持つ） | `HeldExists` 違反 |
| `gcreg_bug_stalemark` | 記録の CAS で、マークの後の登録を除く | `HeldExists` 違反 |

`gcreg_design` でも削除は起きる（別の検査で確かめた）。

### 18.4 Lean

TLA+ は小さな上限での網羅だが、Lean の定理は大きさを限らない。14 の定理はいずれも標準の公理（`propext`、`Classical.choice`、`Quot.sound`）だけに依存し、`sorry` を使わない。

| 定理 | 内容 |
|---|---|
| `History.walk_monotone` | 条件付き作成は、復元が読む履歴を伸ばすだけ |
| `History.acked_prefix_official` | 保存済みの連続したチャンクは、復元が読む履歴の接頭部 |
| `History.seal_final_goal` | 封印の後は、どのキーへの作成も履歴を変えない |
| `History.non_contiguous_ack_unsafe` | 前が空いたまま後ろのチャンクで応答するのは危険（反例） |
| `Origin.walk_from_origin` | 保存済みの連鎖から辿った履歴は、連鎖の中身と、連鎖の次から辿った履歴をつないだもの |
| `Origin.walk_ignores_below` | 起点から辿る走査は、起点より下のキーを読まない |
| `Barrier.mod_lsn_complete` | 可視化の前に上げれば、木ごとの LSN は読んだ対象への可視コミットをすべて覆う |
| `Barrier.reply_reveals_only_durable` | 目標まで待てば、応答が依存するコミットは耐久化済み |
| `Barrier.target_within_published` | 目標は公開済みコミットの最大 LSN を超えない |
| `Pipeline.capacity_below_bandwidth` | 処理量は W·b 未満 |
| `Pipeline.chunk_sizing` | 帯域の割合 p/q に必要十分なチャンクの大きさ |
| `Pipeline.serial_bounded_is_latency_bound` | 直列・上限付きチャンクは `C_max / a` で頭打ち |
| `Pipeline.eager_capacity` | チャンクの大きさを選べるなら、持続できるのは `λ < W·b` のときに限り、遅延 a に依存しない |
| `Pipeline.bounded_chunk_capacity` | 上限 `C_max` のチャンクでは、処理量は `W·C_max / (a + C_max/b)` を超えない |

### 18.5 見つかった穴と設計への反映

**設計時の検証（2026-11-26）**

1. 直列の PUT は 1 接続の帯域で頭打ちになる（模擬実験、`Pipeline.serial_bounded_is_latency_bound`）。→ パイプライン化（§6）。
2. 空きができ次第切り出す方式は、中央値の遅延と PUT 数を悪化させる。→ 適応型の切り出しとヘッジ（§6.2、§6.3）。
3. 再起動で同じエポックの連番を使い続けると、死んだ writer の遅れた PUT と衝突する。→ 起動ごとのエポック（U6）。
4. 封印を置かずに走査だけで終端を決めると、正式な履歴が縮む。→ 条件付き作成の封印（T3）。
5. 412 を成功とみなすと、封印や他人のチャンクを自分のものと誤る。→ チェックサムの照合（U3）。
6. 追い越された古い候補が、新しい転送のエポックを封印しうる。→ エポック記録の `tgen`（T4）。
7. ローカル WAL を無条件に再利用すると、正式な履歴と食い違う。→ 一致の確認（T5）。後に、未送信の末尾そのものを使わない規則にした（下のレビューの 4）。
8. S3 永続化 LSN を超えるマニフェストは、正式な履歴と食い違いうる。→ §9.2 の手順 3。
9. 内容のハッシュをキーにすると、GC と競合して参照先が消える。→ アップロードごとの新しいキー（§5.4）。
10. GC の年齢判定はマークの時刻で行い、`RefWindow` ＜ `Grace` が要る。→ 後に、時刻による判定そのものを確定の規則に置き換えた（下のレビューの 3、§13）。
11. 現行の D4 は、索引で行が無かった読み取りの依存を記録しない。→ 木ごとの公開済み変更 LSN（§7）。ローカルモードにも適用する。
12. S3 同期モードの安全性は、ローカルの fsync に依存しない。→ アップロードを fsync と並行にする（§6.4）。

### 18.6 モデルに含めていないもの

- 読み取りの隔離とリース、再生区間の閉包（登録したマニフェストから先の連鎖を根に含めること。レビューの小さなモデルでだけ確かめた。`GcRegistry.tla` は登録を個々のオブジェクトとして表す）、マニフェストの連鎖、standby の適用、LSN のパディング、マルチパート、範囲キャッシュ、ページ対応表。
- チェックポイントの再生開始 LSN と被覆上限の区別。`S3Wal.tla` のチェックポイントは内容の接頭部だけを持つ。T5 の再生開始の条件は、レビューが現行のストレージで確かめた。
- WAL の GC。封印の削除だけは `s3wal_bug_sealgc` で扱い、起点から辿る走査は Lean で示した（§18.4）。
- `ObjectGc.tla` は、根を正式な参照のすべて（`refs`）とし、マニフェストからの引き継ぎと install の一覧を区別しない。本文の GC は WAL を読まず、根を有効なマニフェストの参照と install の一覧に限る。その代わり、被覆上限より後ろに参照がありうるオブジェクトを確定済みとしない（§13.2）。この対応と、確定の水位（モデルではオブジェクトごとの確定の宣言として表す）の導き方はモデルに含めていない。WAL 側のモデルとも結合していない。
- `ReplyBarrier.tla` の読み取りは、スナップショットの取得と観測を 1 つの操作で行う（§18.2）。
- 模擬実験の遅延分布は仮定であり、実際の S3 の分布（特に裾の重さと相関）で結論が変わりうる。P0 の実測で確かめる。

## 20. 実装順と受け入れ条件

| 段階 | 内容 | 受け入れ条件 |
|---|---|---|
| P0 測定 | 使う S3（同じリージョンの Standard、同じ AZ の Express One Zone）で、PUT・GET の遅延分布、1 接続の帯域、412・409 の挙動を測る | 模擬実験の仮定を実測値で置き換えて再実行し、W・`C_max`・`linger`・ヘッジの閾値の既定値を決める |
| P1 バリアの穴 | §7 をローカルモードで実装する（S3 に依存しない） | `barrier_*` の各設定に対応する回帰試験。索引で 0 件を返す読み取りが、未耐久の DELETE を待つこと。LSM への反映と版の公開の間に索引を読んでも待つこと。スナップショットの後に DELETE がコミットされ、その後に開いたカーソルで読んでも待つこと |
| P2 圧縮の WAL 化 | `kInstallColumnar`、原子的な差し替え、ローカル TLCS の世代つきの名前、チェックポイント記述子 | 圧縮と再圧縮の各段階でクラッシュを注入し、索引とチェーンが一致し、旧ベースから再生できること。install → hydrate・更新 → ファジーなチェックポイント → 同じ install の再生でも一致すること。再生開始 LSN と被覆上限が、復元の前後で正しいこと |
| P3 形式と非同期送信 | クライアント、チャンク、パイプライン（ヘッジ専用の枠）、マニフェスト（親の連鎖、起点、install の一覧、確定の水位、固定）。応答はまだローカル基準 | 別のホストで、有効なマニフェストと WAL から単一ノードと同じ結果に復元できる。PUT の結果不明、412、409、403、遅延した到着、遅れて届くマニフェストを注入する |
| P4 同期モードと転送 | `ReplyLSN`、エポック、転送のコマンド（T2 の確認、T5 の切り詰め）、封印を消さないこと、送信済み WAL のキャッシュ化 | S3 の確認の後、マニフェスト更新の前に primary のディスクを失っても、成功済みの更新が残る。昇格の後にコミットし、もう一度再起動しても残ること。ゾンビ、書き続ける旧 writer、二重の転送、T1 の直後に止まる候補、途中で止まった候補、遅延した PUT を注入する。実装の実行トレースを `S3Wal.tla` に照合する |
| P5 GC | マーク・スイープ（確定の規則）、読者の登録、WAL の回収 | `objgc_*` の各設定に対応する回帰試験。送信を長く止めた後に再開しても参照が解決すること。封印とエポック記録が残ること。登録した再生区間で、途中で置き換えられたオブジェクトも含めて追従できること。結果の分からない DELETE を残して GC を止め、別の GC が引き継げること |
| P6 差分のベースと範囲キャッシュ | LSM ランのオブジェクト化、blocks の範囲、範囲キャッシュ、TLCS の範囲読み、TLCS の分割 | ローカルディスクの数倍の DB で、ロード・走査・TPC-H が正しく完走し、温まったキャッシュでの速度が低下しないこと |
| P7 hot standby | コミット単位の原子的な適用、エポックの追跡、検証済みの位置からの昇格 | 長いクエリの最中の適用、エポックの切り替え、昇格の時間 |
| P8 PITR とクローン | 復元の停止位置、クローン（メタデータの作り直し、5 GB を超えるオブジェクトのコピー） | PITR の後の再開。本番と同じバケットポリシーの下でクローンを作れること。元のクラスタを消してもクローンが読めること |

P1 と P2 は S3 に依存せず、ローカルモードの正しさも上げるので先に行う。GC の削除処理は P5 で入れるが、封印を消さないこと、確定の水位、マニフェストの連鎖と起点は最初の WAL・マニフェストの形式に入るので、P3 と P4 で決める。性能は、単発と並行の `COMMIT` の p50・p99、TPS、PUT の数と遅延の分布、冷えた走査の帯域、S3 停止時の滞留、昇格にかかる時間で測る。

## 21. 採らなかった案

| 案 | 理由 |
|---|---|
| 1 件ずつの直列 PUT（旧版） | 1 接続の帯域で頭打ち（§16.2） |
| 空きができ次第切り出す | 中央値の遅延と PUT 数が悪化する（§6.2） |
| Express One Zone の追記で 1 オブジェクトに書き足す | 書き込み位置の条件で 1 件ずつ直列になる |
| マルチパートの各パートを WAL にする | 完了するまで読めず、耐久化の証明にならない |
| DynamoDB や etcd で書き込み権を管理する | 依存が増える。S3 の CAS で足りる |
| 書き込みを止めて静止ベースを取る（旧版） | 現行のチェックポイントで足りる |
| standby で再圧縮する（旧版） | primary と配置がずれ、standby ごとに計算が重複する |
| 内容のハッシュをキーにする | GC と競合する（§13、§18.3） |
| `BufferedLSN` まで待つ（旧版） | 不要な待ちが入る（§7.4） |
| 再起動で同じタイムラインを再開する（旧版） | 遅れた PUT と衝突する（§18.1） |
| 再起動で未送信の末尾を新しいエポックで送る（前版） | 再起動直後の読み取りと GC の保証が崩れる（§11.2） |
| 旧エポックの封印を保持期間で消す | 遅れた PUT が成功し、成功を返したコミットが失われる（§5.3） |
| 作成時刻と猶予期間による GC（前版） | 送信の停止が猶予を超えると参照先が消える（§13.3） |
| 封印だけを確定の条件にする | 長いエポックで、置き換えられたオブジェクトを次の転送まで消せない（§13.2） |
| WAL への追記の前に、GC から見える予約を置く | 確定の規則で足りる。予約は書き込みと片付けを 1 つずつ増やす |
| Raft による複製 | 単一 writer の前提では S3 の条件付き書き込みで足りる。[分散設計](../distributed.md)は別にある |
