# 実行モデル

## 1. 論理計画から物理的な反復子へ

関係代数の選択、射影、結合、集約は、問い合わせ結果を定める。物理実行計画は、その結果を求めるアルゴリズムとデータの受け渡し方を定める。たとえば、表を全走査するか索引を使うか、結合にハッシュ法とマージ法のどちらを使うか、どこで整列するかを選ぶ。

実行器は物理計画木の各ノードに対応する状態を持つ。典型的な木は次のようになる。

```text
Limit
└─ Projection
   └─ Selection
      └─ HashJoin
         ├─ FullScan(A)
         └─ IndexScan(B)
```

親は子にデータを要求し、子も同じように下位の子へ要求する。根で始まった要求は葉の走査まで進み、各ノードが結果を順に加工して親へ返す。この方式を要求駆動型（demand-driven）の pull 型、または Volcano 型反復子モデルと呼ぶ。

## 2. `Next` と終了契約

`ExecutorBase` は、すべての要求駆動型演算子に共通するインターフェースである。仮想関数 `Next`、既定実装を持つ `NextBatch`、計画を表示する `Dump` / `Explain`、実行状態を返す `GetStatus` を定めている。`Executor` は `ExecutorBase` を共有所有するポインタの別名であり、親はこのポインタを介して子の寿命を管理する。カーソル状態が意図せず複製されないように、`ExecutorBase` はコピー操作とムーブ操作を禁止している。

行指向の基本操作は次の形である。

```text
Next(行の出力先, 物理行位置の出力先) -> 行を返したか
```

`true` は 1 行を返したことを表す。`false` は「正常な末尾」と「実行失敗」の両方に使われるため、呼び出し側は停止後に状態を確認する。

```text
while child.Next(row, position):
    consume(row)

if child.status is error:
    propagate(child.status)
else:
    end of stream
```

失敗状態は、最初の失敗だけを残す方式（sticky status）で保持する。後続の失敗で最初の原因を上書きしない。ラッパー演算子は、自身で失敗していなくても、子の失敗を親へ伝える必要がある。伝えなければ、処理途中の失敗と正常な入力終了を区別できない。

例外を通常のデータベース制御に使わず、式評価、型変換、ストレージ読み出し、制約検査などの失敗を状態値として伝播する。したがって、各演算子には次の二つが必要になる。

1. 子が止まったときにその状態を確認する。
2. 自身の部分結果を返した後で失敗を成功扱いにしない。

## 3. 行指向とバッチ指向

バッチ指向の基本操作は次の形である。

```text
NextBatch(列指向バッチの出力先, 最大行数) -> 返した行数
```

0 行も正常な末尾と失敗の両方を表すため、停止後の状態確認は `Next` と同じである。標準の最大バッチ幅は 1024 行である。

演算子が `NextBatch` を実装していない場合、既定実装は `Next` を繰り返してバッチを組み立てる。結果は変わらないが、行ごとの仮想関数呼び出し、行から列への詰め替え、値オブジェクトの生成が必要になる。走査、選択、射影、集約などの専用バッチ処理は、列配列と選択ベクトルを直接扱って、この費用を減らす。

逆に、バッチ優先の演算子が行 API を提供するときは、子から一つのバッチを受け取り、内部カーソルで 1 行ずつ返す。したがって、行 API とバッチ API を混在させても意味は変わらないが、境界が増えるほど変換コストは増える。

## 4. パイプライン

入力の一部を受け取った時点で出力を返せるものを、ストリーミング演算子と呼ぶ。走査、選択、射影、制限が代表例である。これらを連結すれば、中間結果全体を保存せずに一つの実行パイプラインを構成できる。

全入力または片方の入力を読み終えるまで出力できない演算子を、パイプラインブレーカーと呼ぶ。

| 分類 | 例 | 出力開始条件 |
|---|---|---|
| 完全ストリーミング | `Selection`、`Projection`、`Limit` | 最初の入力行またはバッチ |
| 片側をブロック | `HashJoin`、`NestedLoopJoin` | ハッシュ表の構築側または右側の実体化後 |
| 全体をブロック | `Sort`、`Window`、グルーピング集合 | 全入力の読み終わり後 |
| 明示的な境界 | `Materialize`、`Exchange` | 入力を保持または分配した後 |

パイプライン化には三つの利点がある。

- 最初の行までの待ち時間が短い。
- 中間結果全体を保持する必要がない。
- `LIMIT` のような上位演算子が早期終了すると、下位の不要な処理も止められる。

ただし、ハッシュ表の構築、完全な順序付け、ウィンドウの前後行参照には、中間状態が必要である。物理計画では、このようなブロッキング処理を境界として明示し、メモリ制限を超えた場合のスピル方法も決める。

## 5. 物理行位置

走査結果には、行の値に加えて物理行位置が付くことがある。物理行位置は、ページ識別子とページ内スロットの組のように、行の格納場所を示す。主な用途は次のとおりである。

- `UPDATE` と `DELETE` が元の行を特定する。
- ビットマップ走査が索引結果からヒープ行を読み出す。
- 行の値が同一でも別の物理行として扱う。

選択、射影、制限、整列のように「同じ入力行」を並べ替えたり列だけ変えたりする演算子は、原則として位置を保存する。結合や集約は複数行から新しい行を合成するため、単一の正しい位置を定義できない。外部結合の保存側、準結合・反結合の左側など、出力が一つの入力行と一対一で対応する場合だけ位置を引き継げる。

物理行位置が必要な更新計画で途中の演算子が位置を失うと、値は正しく見えても更新対象を確定できない。このため、スキーマだけでなく位置保存性も物理特性である。

## 6. スナップショットと可視性

走査は単に格納されている最新版を読むのではない。トランザクションのスナップショットに対して可視な版を選ぶ。索引が物理行を指していても、索引項目の存在だけでは可視性を証明できないため、必要に応じてヒープ側の版を確認する。

更新目的の走査では、短時間のページラッチ、論理的な行ロック、MVCC の書き込み意図を区別する必要がある。

- ページラッチはメモリ上のページ構造を短時間保護する。
- 行ロックはトランザクション間の論理的競合を調停する。
- 書き込み意図は、可視版と更新予定版の関係を記録する。

並列走査が満杯の出力キューを待つ間にページラッチを保持すると、他のワーカーやバッファ管理を止める可能性がある。そのため、バッチをローカルに完成させ、ページ保護を解放してからキューへ投入する。

## 7. SQL の値意味論

物理演算子は C++ の比較や真偽値をそのまま使えない。SQL の意味論として少なくとも次を統一する必要がある。

### 7.1 三値論理

述語結果は `TRUE`、`FALSE`、`UNKNOWN` の三値である。`WHERE` と `HAVING` は `TRUE` の行だけを残し、`FALSE` と `UNKNOWN` を捨てる。通常の等値結合では `NULL = NULL` も `UNKNOWN` なので一致しない。NULL 安全な等値比較を明示したキーだけは、`NULL` 同士を一致させる。

### 7.2 重複

関係演算の中間結果は集合ではなく多重集合である。`UNION ALL`、結合、通常の射影は重複を保存する。`DISTINCT`、`UNION`、`INTERSECT` など、意味論が要求する場所でだけ重複を除く。

### 7.3 `NULL` と集約

`COUNT(*)` は行を数え、`COUNT(expr)` は非 `NULL` 値を数える。`SUM`、`AVG`、`MIN`、`MAX` などは `NULL` 入力を無視し、有効入力がなければ通常 `NULL` を返す。グループなし集約は空入力でも 1 行を返すため、`COUNT(*) = 0` という結果を表現できる。

### 7.4 浮動小数点と `NaN`

通常の IEEE 比較では、`NaN` は自身とも等しくない。しかし、重複除去、グループ化、整列、ウィンドウの同順位判定では、`NaN` の扱いを決める必要がある。共通の重複判定キー、グループキー、ウィンドウの同順位判定では、すべての `NaN` を同じ値として扱う。

一部の専用処理は、生の比較またはバイト列への符号化を使うため、この共通規則に従わない。順序内で `NaN` を置く位置も、`Sort`、共通の `ORDER BY` 比較、パーセンタイル処理で異なる。各演算子の規則は対応する章で説明する。

## 8. 順序という物理特性

SQL の結果順は `ORDER BY` がなければ保証されない。それでも演算子内部では、次の区別が性能と正しさに影響する。

- `IndexScan` は索引キー順を生成できる。
- `Sort` は指定された全体順序を生成する。
- `MergeJoin` は入力に順序を要求する。
- `IncrementalSort` は既存のキー接頭辞順を要求する。
- `ParallelScan` はワーカーの完了順になるため表の物理順を保証しない。
- `HashJoin` とハッシュ集約は一般に入力順を保存しない。

「現在そう見える順番」と「演算子が保証する順番」は異なる。物理計画は後者だけを利用しなければならない。

## 9. 代表的なコスト軸

同じ論理演算にも複数の物理実装がある。選択は単純な漸近計算量だけでは決まらない。

| 軸 | 問い |
|---|---|
| 入力行数 | 全走査する行は何行か。選択後は何行になるか。 |
| 行幅 | ハッシュ表、整列キー、コピーする行のバイト数はどれだけか。 |
| 選択度 | 索引プローブで十分絞れるか。 |
| 既存順序 | 整列を省けるか、増分整列で済むか。 |
| 重複度 | 等値キーのランが大きく、結合出力が膨張しないか。 |
| 作業メモリ | ハッシュ表や整列済み列（run）がメモリ内に収まるか。 |
| 最初の行までの時間 | 全件完了より早期応答が重要か。 |
| 並列性 | 分割可能か。共有状態の競合が利益を上回らないか。 |
| 再利用 | 相関しない内側結果や実体化結果を何度読むか。 |

たとえば、ハッシュ結合の期待時間は `O(L + R + 出力)` だが、メモリに収まらなければ分割 I/O が加わる。マージ結合は既に整列済みなら線形だが、事前整列が必要なら `O(L log L + R log R)` になる。索引結合は左 1 行ごとの探索が `O(log R)` でも、左が大きいとランダムアクセスが支配する。

## 10. 早期終了、取り消し、後始末

`LIMIT` は、必要な行数を得た後に子の読み出しを止めるため、走査 I/O と式評価を削減できる。ただし、バックグラウンドワーカーを使う並列走査や並列結合では、親が早期終了したときに停止を要求し、キュー待ちを解除してからスレッドの終了を待つ必要がある。

同様に、スピルファイル、メモリ予約、スケジューラの利用許可は RAII で所有し、正常終了、失敗、早期終了のどの場合にも解放する。実行器のデストラクタは単なるメモリ解放ではなく、実行中資源の最終的な取り消し境界でもある。

## 11. 説明出力と診断

各演算子は計画木を表示する `Dump` / `Explain` を持つ。説明出力は結果計算とは独立しており、子の構造、結合種別、利用索引、整列キー、推定行数などを観察するためのものになる。

実行時の診断には、推定行数と実測行数のずれを表す q-error（q 誤差）を利用できる。

```text
q-error = max(actual, estimated) / max(min(actual, estimated), 1)
```

1 に近いほど推定が良く、大きいほど過大・過小推定が深刻である。行数プローブはデータを変えずにこの情報と経過時間を記録し、物理アルゴリズム選択の検証に使える。
