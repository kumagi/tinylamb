# データ変更

データ変更実行器は、読み取り実行器が選んだ行または生成した行を、同じトランザクションの表操作へ渡す。実行器自身はコミットせず、表の行 API を通して挿入、更新、削除を依頼する。MVCC の版、索引の更新、書き込み意図、WAL は、下位の表、トランザクション、ストレージの各層が処理する。

更新系の `Next` は通常、最初の呼び出しで変更を実行し、処理件数を表す要約行を一度だけ返す。次の呼び出しでは行を返さない。要約行は格納済みの行に対応しないため、`RowPosition` は無効である。

## 1. 共通の実行契約

### 1.1 行位置

`Update` と `DeleteExecutor` の入力には、値に加えて対象行の有効な `RowPosition` が必要である。行位置を使うと、値が同じ二行を区別し、走査時に見つけた版を正しい物理行へ対応付けられる。通常は DML 用の走査が行位置を返し、フィルタと射影が後段まで保存する。

`Insert` は新しい行を作るため、入力位置を使わない。`MergeExecutor` は対象表の走査から位置を収集し、入力側の位置は参照しない。

### 1.2 文内検査と原子性

一部の演算子は、変更を始める前に全対象を集め、主キーと外部キーを検査する。この検査により、処理の後半で判定できる制約違反については、途中まで変更した後でエラーになる事態を減らせる。ただし、すべての失敗を事前に検出するわけではない。表操作、I/O、後続の入力、`ASSERT_ROWS_MODIFIED` は、変更を始めた後で失敗する場合がある。

各実行器は、それまでに行った変更を自分では取り消さない。文の原子性を保つには、失敗を受けた呼び出し側がトランザクションを中止し、UNDO と WAL の処理で変更を巻き戻す必要がある。失敗した実行器を同じトランザクションで再び呼び出すことはできない。

### 1.3 主キーと外部キーの補助検査

主キーの補助検査を有効にした処理は、第一列をキーとみなし、表全体を事前に走査する。キーは値の文字列表現で管理する。`NULL` には番兵となるバイト列 `0x01 4e 55 4c 4c` を割り当てるため、複数の `NULL` も重複と判定する。この番兵はエスケープしない。そのため、文字列キーが同じ 5 バイトと完全に一致すると、`NULL` と衝突する。

外部キーの子側検査では、親表の非 `NULL` キーを、型タグ付き文字列の多重集合へ入れる。子キーが `NULL` なら許可する。非 `NULL` であり、親キーの多重集合に存在しなければ失敗する。親側を更新または削除するときは、参照元の表を走査し、参照が残る変更を `NO ACTION` として拒否する。連鎖変更、`SET NULL`、遅延制約は行わない。

これらのキースナップショットを作る表反復子は、`IsValid()` だけを調べて反復し、無効になった後に `GetStatus` を確認しない。I/O などの障害が例外を発生させず、反復子の状態だけに記録された場合は、不完全な主キー集合または親子キーのスナップショットを正常なものとして検査に使う可能性がある。正しい制約判定には、これらの走査が正常に完了することも必要になる。

## 2. `Insert`

`Insert` は、入力が返す各行を対象表のスキーマに従う一行として扱う。最初の呼び出しで入力を末尾まで読みながら挿入し、成功すると次の行を一度だけ返す。

```text
["Insert Rows", modified_count]
```

入力値の型変換、列名から出力列位置への並べ替え、既定値の解決は、通常この演算子へ渡す前に完了している。

### 2.1 競合時の動作

| モード | キーが既存の場合 |
|---|---|
| `default` | キー重複として失敗 |
| `ignore` | その入力行を捨てる |
| `upsert` | 指定した対象列だけを既存行へ上書きする。指定列が空なら行全体を置換 |
| `replace` | 既存行全体を入力行で置換 |

`default` 以外の競合処理は、主キー検査が有効な表でだけ使える。演算子は処理の開始時に対象表を全走査し、第一列のキーから既存キーの集合と `RowPosition` の表を作る。新しく挿入したキーもこの集合へ追加するため、同じ入力バッチ内の後続行との重複も競合として扱う。

新規挿入は一件の変更として数える。新規行に対して、同じキーを持つ後続の `upsert` または `replace` を行った場合は、同じ論理行を一度だけ数えるため件数を増やさない。処理開始前から存在したキーに対する `upsert` と `replace` は、入力行ごとに件数を増やす。`ignore` した行は数えない。

### 2.2 外部キー

各子キーは、処理開始時に作った親キーの多重集合と照合してから挿入または更新する。自己参照する表では、同じ文で先に挿入した親キーを多重集合へ追加するため、後続の入力行から参照できる。ただし、新しい行自身の親キーを集合へ追加するのは子側の検査後である。表にまだ存在しないキーを、同じ一行だけで自己参照することはできない。

`upsert` または `replace` で自己参照表の既存行を変更した後は、親キーの多重集合を表から作り直す。古いキーを推測して差し引くのではなく、その時点のトランザクションビューと一致させるためである。

### 2.3 エラーと件数検査

表の `Insert` または `Update` が一意性制約などで失敗した場合は、件数を増やさず、競合エラーとして終了する。入力が停止した後は、必ず入力の状態を確認する。

`ASSERT_ROWS_MODIFIED n` が指定されている場合は、処理件数と `n` を最後に比較する。不一致が分かる時点では、変更がすでにトランザクションへ記録されている。エラーを受けた呼び出し側は、トランザクションを中止する必要がある。

この演算子は、対象表全体のキーマップと外部キーの多重集合に `O(対象行数)`、入力内のキー集合に `O(入力内の異なるキー数)` の追加メモリを使う。入力行自体は全件保持せず、一行ずつ処理する。

## 3. `Update`

`Update` の入力は、更新後の完全な行と、対象の `RowPosition` を返す。演算子は入力をすべて `pending` 配列へ取り込み、入力の状態と制約を確認した後、対象表を順に更新する。変更を始めるまでは完全なブロッキング処理となり、対象行数を `M` とすると、少なくとも `O(M)` の行メモリを使う。

### 3.1 主キーの事前検査

第一列のキーを変更する場合は、次の順序で文全体を検査する。

1. 対象表の全行について、キーとその個数を数える。
2. `pending` の各行について古いキーを表から読み、現在有効なキーの集合から一時的に取り除く。
3. 更新後のキーが二つの `pending` 行で重複せず、更新対象外の有効行とも衝突しないことを確認する。

この手順により、二行が互いのキーを交換する更新を許可できる。一方、二行が同じ新しいキーを使う場合や、更新対象外の行が持つキーを使う場合は、一行も書き換える前に失敗する。`NULL` も通常のキーと同じく、一つだけ許可する。

### 3.2 外部キーの事前検査

子側のキーが変わる場合は、新しい非 `NULL` キーが親表のスナップショットにあるかを調べる。親側のキーが変わる場合は、古い非 `NULL` キーを参照元の表がまだ参照していれば、`NO ACTION` として失敗する。検査に必要な変更前の行は、変更を始める前に対象表からすべて読む。

すべての検査が終わると、`pending` の順に `Table::Update` を呼ぶ。自己参照表の親キー多重集合は、更新に成功するたびに古いキーを減らし、新しいキーを増やす。ただし、主な制約判定は書き込み前のスナップショットに対して行う。

成功時の出力は次である。

```text
["Update Rows", updated_count]
```

表の更新、入力の読み出し、外部キー検査、主キー検査のいずれかに失敗すると、最初のエラーを状態に保持する。`ASSERT_ROWS_MODIFIED` は全更新の後に比較するため、不一致の場合はトランザクションのロールバックが必要になる。

## 4. `DeleteExecutor`

`DeleteExecutor` の入力は、削除対象の値と `RowPosition` を返す。削除に使うのは行位置であり、値そのものは使わない。演算子はまず、すべての位置を `pending` 配列へ集める。入力が失敗した場合は、一行も削除しない。

親側の外部キーがある場合は、各対象の削除前の行を読み、参照されるキーごとに子表を走査する。同じ文で削除する位置は無視する位置の一覧に入れる。この処理により、自己参照のように削除集合の内部だけで完結する参照を理由として、親行が残ることを防ぐ。削除後も残る子行が一つでも古いキーを参照していれば、削除を始める前に失敗する。

検査後、位置列の順に `Table::Delete` を呼ぶ。途中の削除に失敗すると成功を表す要約行は返さず、ロールバックはトランザクション境界に任せる。成功時は次の行を一度だけ返す。

```text
["Delete Rows", deleted_count]
```

`ASSERT_ROWS_MODIFIED` は削除後に確認する。追加メモリは対象位置数に比例する。外部キー検査は、親側の対象行ごとに子表を走査する。索引を使わない現在の処理では、対象行数を `M`、子表の行数を `C` とすると、計算量は最悪 `O(MC)` になる。

## 5. `TruncateExecutor`

`TruncateExecutor` は、ストレージファイルを物理的に切り詰めない。トランザクションのスナップショットで表を全走査し、すべての `RowPosition` を配列へ集める。その後、各位置を通常の `Table::Delete` へ一つずつ渡す。したがって、MVCC、索引、WAL の変更処理は通常の削除と同じである。

最初の呼び出しで実行済みフラグを立て、すべての位置を処理した後、削除に成功した件数だけを持つ一列を返す。

```text
[deleted_count]
```

個々の `Delete` が失敗した場合は件数を増やさない。ただし、そのエラーを自身の状態には記録せず、残りの位置を処理して要約行を返す。外部キー、`ASSERT_ROWS_MODIFIED`、ラベル列も扱わない。この点は `DeleteExecutor` と異なる。計算量と位置配列のメモリ使用量は、ともに `O(N)` である。

先に行う全走査も、反復子の状態を確認しない。走査が途中のエラーによって無効になった場合は、それまでに集めた位置だけを削除し、部分的な成功件数を正常な結果として返す可能性がある。

## 6. `MergeExecutor`

`MergeExecutor` は、入力行と対象表の行を条件付きで照合する。一致した場合は `MATCHED` 句の `UPDATE` または `DELETE` を実行し、一致しなかった場合は `NOT MATCHED` 句の `INSERT` を実行する。最初に対象表の全可視行と位置を `target_entries` へ保存し、その後で入力を一行ずつ読む。

### 6.1 照合

各入力行について、削除済みでも同じ文で挿入済みでもない対象項目を線形走査する。`ON` 条件がなければ、すべての組を一致とする。条件がある場合は、`[対象表の列, 入力の列]` を連結した行に対して評価する。真の場合だけ一致とし、`FALSE`、`NULL`、`ON` 条件の評価失敗は、いずれも不一致として扱う。

一致した対象行ごとに `MATCHED` 句を記述順に調べ、条件が最初に真になった句だけを適用する。句の条件が `NULL` になった場合や評価に失敗した場合は、その句を飛ばす。

- `UPDATE` は代入式を連結行に対して評価し、指定列だけを変更前の行へ上書きする。代入式の評価失敗は問い合わせ全体の失敗になる。
- `DELETE` は保持済みの位置にある行を削除し、その項目を以後の照合から外す。

一つの入力行が複数の対象行に一致すると、そのすべてに処理を適用する。後続の入力行は、以前の入力行が更新した対象項目とも照合する。このときは、更新後の行を使う。同じ対象行に複数の入力行が一致したことを検出して拒否する処理はない。

対象行に一件も一致しなかった入力行についてだけ、`NOT MATCHED` 句を記述順に調べる。条件が最初に真になった `INSERT` 句では、値の式を入力スキーマに対して評価する。値は指定列、または先頭列から順に配置し、指定のない対象列を `NULL` にして挿入する。同じ文で挿入した行は `target_entries` へ記録するが、後続入力の `ON` 条件と照合する候補にはしない。

### 6.2 資源、制約、出力

対象行数を `T`、入力行数を `S` とすると、照合の計算量は `O(ST)`、対象表のスナップショットに使うメモリは `O(T)` である。ハッシュまたは索引による照合、スピル、入力の実体化は行わない。

最初に対象表のスナップショットを作る全走査では、反復子の状態を確認しない。走査が途中のエラーによって停止すると、取得済みの対象行だけで照合を続ける。その結果、本来は一致する入力行を不一致と判定する可能性がある。入力の停止状態は最後に確認するが、対象表のスナップショットには同じ確認がない。

この演算子自身は、`Insert`、`Update`、`DeleteExecutor` が行う主キーの補助検査、外部キーの事前検査、`ASSERT_ROWS_MODIFIED` を実装しない。表 API が返す一意性制約、索引、ストレージのエラーには、元の状態コードを保ったまま MERGE の処理中であることを付記する。すでに行った変更を演算子内で取り消すことはない。

入力が完了し、その状態が成功であることを確認した後、次の行を一度だけ返す。

```text
["Merge Rows", inserted_count, updated_count, deleted_count]
```

## 7. `ReturningExecutor`

`ReturningExecutor` はデータを変更せず、子が返した各行に式の射影を適用する透過ラッパーである。子から一行と `RowPosition` を受け取り、指定された `RETURNING` 式を入力スキーマに対して左から順に評価し、新しい行を返す。位置は子から受け取った値をそのまま転送する。

このラッパーは、変更前または変更後の行を表から取得しない。変更件数の要約行を、変更対象の行列へ展開することもない。標準的な `RETURNING` の結果を作るには、子自身が返却対象の行を一行ずつ返す計画が必要である。`Insert`、`Update`、`DeleteExecutor` の要約行を直接包んだ場合は、その要約行に対する射影になる。

式の評価に失敗すると、そのエラーをラッパーの状態に保持する。一方、子が行を返さず停止した場合は、子の状態を明示的に転送せず、そのまま `false` を返す。このため、親からは子の失敗と正常な末尾を区別できない。このラッパーを実行境界に使う場合は、子の状態を別に確認する必要がある。

## 8. 読み取り計画との接続

更新対象を作る物理計画には次の性質が必要である。

- `UPDATE` / `DELETE` では、走査が可視な版の行に加えて、有効な `RowPosition` を返す。
- フィルタは `UNKNOWN` を除外し、射影は位置を失わずに更新後の行を作る。
- 対象行の同時更新を待つか競合として返すかは、DML 用走査のロック・書き込み意図の設定と、トランザクション層の規則で決まる。
- 整列または実体化を挟む場合も、対象位置を行と一緒に保存する。
- 入力が途中で失敗した後に DML 実行器が正常件数を返さないよう、末尾で子の状態を確認する。

更新件数の要約行は、通常の表スキーマとは異なる。この行を後続の演算子で処理する場合は、ラベルと件数からなるスキーマ、または `TruncateExecutor` の一列スキーマを明示して接続する必要がある。
