# データ表現と実行時資源

## 1. `Row` と `DataChunk`

実行経路には二つのデータ表現がある。

- `Row` は一つのタプルを値の並びとして表す。制御が単純で、相関副問い合わせや行単位のストレージ操作に向く。
- `DataChunk` は同じスキーマを持つ複数行を列方向に保持する。既定容量は 1024 行で、走査、フィルタ、射影、集約のまとまった処理に向く。

`DataChunk` は列配列、列ごとのゾーンマップ、行ごとの `RowPosition`、現在の行数を持つ。スキーマはバッチ中で固定される。入力行を追加すると、各値は対応する `ColumnVector` へ入り、同時に最小値・最大値などの要約と物理行位置が更新される。

```text
DataChunk
├─ ColumnVector 0: [10, 20, NULL, 40, ...]
├─ ColumnVector 1: ["a", "b", "c", "d", ...]
├─ ZoneMap 0: min=10, max=40, nulls=1
├─ ZoneMap 1: min="a", max="d", nulls=0
└─ RowPosition:   [p0, p1, p2, p3, ...]
```

列指向では同じ型の値が連続するため、条件分岐とキャッシュミスを減らせる。たとえば整数列に対する `x < 100` は、行オブジェクトを一つずつ解釈せず、整数配列を連続して走査できる。

## 2. `ColumnVector`

`ColumnVector` は型ごとの実データ配列と `NULL` ビットマップを分離する。

- 整数と日付は 64 ビット整数配列を使う。
- 浮動小数点は `double` 配列を使う。
- 文字列は文字列配列を使う。
- 配列などの入れ子値は一般値の配列に退避する。
- 符号なし整数であることは列の属性として保持する。

`NULL` は値配列中の特別な数値ではなくビットマップで表す。このため、集約カーネルは有効値だけを処理でき、任意のビットパターンをデータとして使える。

列の型がまだ決まっていない空バッチへ最初の非 `NULL` 値を追加したときは、推定された型用の格納領域を具体化する。別バッチから同型の列をコピーするときは、中間の汎用値へ箱詰めせず列配列間で直接転送できる。

論理 AND/OR とビット AND/OR/XOR には列専用集約があり、選択ベクトルがあれば選ばれた位置だけを処理する。

## 3. `SelectionVector` と `ValidityBitmap`

フィルタ後の行をすぐ別バッチへコピーすると、幅広い行ではメモリ帯域を浪費する。`SelectionVector` は生存した行番号だけを保持する。

```text
入力位置:       0 1 2 3 4 5 6 7
述語が真か:     F T F T T F F T
選択ベクトル:   [1, 3, 4, 7]
```

後段の演算子は、この添字を使って必要な列だけを収集する。複数の述語を評価するときは、前の述語が作った選択ベクトルを次の述語へ渡し、候補を順に絞り込む。

`ValidityBitmap` は各位置の真偽をビット単位で持つ。論理演算をワード単位で行えるため、整数添字列を毎回作るより効率がよい場面がある。最終的に出力バッチを作る段階でビットマップを選択ベクトルへ変換する。

SQL のフィルタでは `TRUE` だけが選択される。`FALSE` と `NULL` はどちらも選択ビットを立てない。

## 4. `ZoneMap`

ゾーンマップはバッチごと、列ごとに次を保持する。

- 非 `NULL` 値の最小値と最大値
- `NULL` 数
- 非 `NULL` 値数
- 初期化済みか
- 浮動小数点の `NaN` を含むか

述語 `x > 100` に対して最大値が 80 なら、そのバッチは式を 1 行も評価せず捨てられる。`x = 5` に対して範囲が `[10, 20]` の場合も同様である。これは偽を証明できる場合だけ除外する保守的な最適化である。

次の場合は誤って除外しないよう「一致する可能性あり」と判断する。

- ゾーンマップが未初期化である。
- 比較不能な型、配列、混在型を含む。
- `NaN` を含む。
- 最小値・最大値だけでは三値論理の結果を証明できない。

ゾーンマップは索引ではない。行の位置を直接探すのではなく、既に読み込んだ、または読み込み単位として管理されたバッチ全体を省略する。

## 5. ベクトル式評価

`VectorizedExpression` は式木を列演算へ写像する。列参照は既存ベクトルを読み、定数は同じ値を必要な長さだけ論理的に供給し、算術・比較・論理演算は対応する位置を一括処理する。主な入口は次の三つである。

1. 値式を評価し、結果の `ColumnVector` を返す。
2. 述語を評価し、`ValidityBitmap` を返す。
3. 述語を評価し、直接 `SelectionVector` を埋める。

式全体を列演算へ変換できない場合は、対応できる部分だけをベクトル化し、残りを行単位で評価する。意味の基準は行単位の式評価にあり、高速経路は同じ意味を保つ特殊化として実装する。

### 5.1 式実行の階層

同じ述語・射影式には概ね次の実行経路がある。

| 経路 | 特徴 | 適する状況 |
|---|---|---|
| AST 評価 | 式木を直接たどる | 低頻度、複雑な型、フォールバック |
| バイトコード | 分岐と仮想呼び出しを減らす | 繰り返し実行される一般的なスカラー式 |
| 列ベクトル | 同じ演算を列に適用する | バッチ走査、フィルタ、射影、集約 |
| JIT カーネル | 狭い整数式をネイティブコード化する | 十分に反復される単純な整数述語・算術 |

単純な符号付き整数比較や `column * m + b` 型の射影は、JIT の対象になりうる。入力が短く、コンパイルに要した時間を実行時間の短縮で回収できない場合は、AST またはバイトコードを使う。コンパイルに失敗した場合も問い合わせは失敗させず、意味の基準である一般経路へ切り替える。

### 5.2 共通部分式

同一の決定的な式が一つの射影内で複数回現れる場合、安全な二項式、単項式、`CASE` などは一度計算して再利用できる。乱数、時刻、外部状態に依存する式を同一視すると結果が変わるため、共通部分式除去は決定性が確認できる式だけに適用する。

### 5.3 `SimdComparisonKernel`

`SimdComparisonKernel` は、連続した配列を比較して、条件を満たす位置を `ValidityBitmap` に記録する専用カーネルである。整数と倍精度浮動小数点数では列と定数、または二つの列を比較できる。文字列では列と定数を比較できる。

対応する演算は、等値、非等値、および大小比較四種の計六種である。それ以外の演算を指定すると、すべてのビットを偽にする。

このカーネルは `NULL` ビットマップを受け取らない。呼び出し側は、格納値の比較結果と非 `NULL` ビットマップの論理積を取る必要がある。この処理を省くと、`NULL` 位置に残っている未使用値を条件に合う値と誤認する可能性がある。

名称には SIMD とあるが、特定の命令セットに固有の組み込み関数は使わない。64 ビット単位で結果を作るループを、コンパイラが自動的にベクトル化できる形で記述している。

## 6. `PipelineBreaker`

全体または片側の入力を保持する演算子は、次の診断情報を公開する。

- すでに実体化済みか
- 明示的に実体化を開始する操作
- 保持した行数
- 推定保持バイト数

これにより、実行制御側はパイプライン境界を列挙し、事前実体化、メモリ見積もり、診断表示を行える。`SortExecutor`、`MaterializeExecutor`、`HashJoin`、`BatchNestedLoopJoin`、`ParallelMergeJoin`、`DistributedAggFinalize` などが該当する。

## 7. 問い合わせ作業メモリ

`QueryMemoryBudget` は、プロセス内で一つの問い合わせに使う作業メモリの合計を追跡する。既定上限は 8 GiB であり、その 80% を軟限界とする。軟限界に達すると新しい予約を拒否し、演算子にスピルまたは低メモリ方式への切り替えを促す。上限が 0 の場合は無制限として扱う。

行の概算サイズは、固定長値、文字列の内容、配列要素などを合計して求める。メモリアロケータが実際に確保した量とは一致しないが、すべての演算子が同じ尺度で判断するための近似値になる。

`QueryMemoryCharge` は、予約済みのバイト数を RAII で管理する。オブジェクトの破棄、ムーブ、明示的な解放のいずれでも二重計上を避ける。問い合わせが失敗または早期終了した場合も、予約量を全量返却する。

## 8. 演算子単位のメモリ予約

`OperatorMemoryReservation` は一つの演算子に次の状態を持たせる。

- 演算子名
- 個別上限
- 現在の割当量
- 縮退状態
- 上限到達時のスピル・コールバック

`TryAllocate` がその場で確認する上限は、演算子ごとの個別上限だけである。個別上限を超えるとコールバックを呼び、低メモリ方式へ切り替えたことを記録して、呼び出し側へ失敗を返す。

個別予約に成功すると、使用量を全体の `QueryMemoryBudget` へ強制的に加算する。この加算自体は、問い合わせ全体の軟限界を検査しない。全体の軟限界を理由にスピルする演算子は、予約前に `CanReserve` を別途調べる必要がある。必須の小さな管理構造には個別上限を無視する強制予約も使え、その場合も全体への計上は続ける。

予約を拒否されても、必ずしも問い合わせを失敗させる必要はない。整列なら現在の整列済み列（run）をディスクへ書き出し、ハッシュ結合なら入力を区画に分け、集合演算ならハッシュ区画をスピルできる。このように、演算子は使用メモリの少ないアルゴリズムへ切り替えられる。

## 9. `SpillFile`

`SpillFile` は一時的な行ストアである。行だけを保存するモードと、行に `RowPosition` を添えて保存するモードを持ち、同じファイル内で両モードを混在させない。

ファイルの先頭には行数を記録するヘッダがあり、書き込みの完了時に確定値へ更新する。読み出し方法は、全行をメモリへ戻す方法と、行をコールバックへ一つずつ渡す方法の二つである。行数の不一致、ファイルの途中での終端、I/O の失敗は、いずれも実行エラーとして報告する。

一時ファイルは、所有するオブジェクトを破棄すると削除される。ムーブ後は新しい所有者だけが削除を担当する。そのため、正常終了に加えて、式評価の失敗、取り消し、`LIMIT` による早期終了でも一時ファイルは残らない。

スピルは単に「メモリ内容をディスクへ置く」だけではない。後で効率よく処理できる形にする必要がある。

- `SortExecutor` は複数の整列済み列を作り、最後に k 路マージ（k-way merge）する。
- `HashJoin` は同じハッシュ規則で両入力を区画化し、対応区画だけを再読する。
- 集合演算は値を共通型へ正規化し、同じ区画へ入るよう再ハッシュする。

## 10. `NumaArena`

並列演算で小さな領域を大量に個別確保すると、メモリアロケータのロックと管理情報を扱う時間が大きくなる。`NumaArena` は、ワーカーごとに追記型アロケータ（bump allocator）の区画を用意する。各ワーカーは、他のワーカーと競合せずに連続領域からメモリを確保できる。

一つの区画は、既定で 64 KiB のブロックを持つ。領域が足りなくなるとブロックを追加する。`Reset` は割り当て位置を先頭へ戻し、区画全体を再利用可能にする。配置したオブジェクトごとのデストラクタは呼ばれないため、格納できるのは自明に破棄できる型に限られる。

このアリーナは、OS による厳密な NUMA 配置を保証しない。目的は、領域をワーカーごとに分けて、メモリ確保時のロック競合を避けることにある。

## 11. `QueryScheduler`

負荷の高い問い合わせを同時に実行し、それぞれが内部並列度を最大にすると、CPU とメモリの競合が起こる。`QueryScheduler` は、CPU スロット数とメモリ量を一組にした利用許可（lease）を発行して、この競合を制御する。

要求量が総容量を超える場合は、総容量まで減らす。要求は FIFO のチケット順で待機する。`ScheduledExecutor` は、最初に `Next` または `NextBatch` を呼ばれたときだけ利用許可を取得し、入力終了または自身の破棄まで保持する。計画木全体を一つの問い合わせとして予約するため、各ノードが同じ資源を重複して予約することはない。

記録する指標は、取得回数、待ち時間、競合が発生した取得回数である。利用許可は RAII で管理されるため、実行の失敗や親の早期停止でも CPU とメモリの枠を返却する。

## 12. キューとバックプレッシャー

並列走査などでは、ワーカーが作ったバッチを有界キューへ入れ、消費側が取り出す。キューの大きさに制限がないと、消費が遅れたときに入力全体と同程度までメモリ使用量が増える。有界キューでは、満杯になると生産側が待機するため、生産速度が消費速度以下に抑えられる。この制御をバックプレッシャーと呼ぶ。

キューを待つ間は、ページラッチや大きな一時領域を保持しない。取り消し時には、停止フラグと条件変数を使って全ワーカーの待機を解除する。ワーカーが失敗した場合は、最初のエラーを保持する状態へ記録する。
