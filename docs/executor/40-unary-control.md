# 単項変換と実行制御

単項演算子は、一つの子から行を受け取る。`Selection` は条件に合う行だけを残し、`Projection` は列を組み替え、`Limit` は返す行数を制限し、`Materialize` は入力を保存する。いずれも入力は一つだが、ストリーミングの可否やメモリ使用量が異なる。

## 1. `Selection`

`Selection` は入力スキーマ上の述語を評価し、結果が `TRUE` の行だけを返す。`FALSE` と `NULL` は除外する。行の値、列順、相対順序、`RowPosition` は変えない。

### 1.1 バッチ処理

行 API も内部ではバッチ処理を使う。子からバッチを取得した後、次の順で高速経路を試す。

1. 単純な列と定数の比較なら、バッチの `ZoneMap` で不一致を証明する。
2. 十分な反復があり、述語が符号付き `INT64` 列と定数の単純比較なら JIT カーネルを試す。
3. 述語全体をバイトコード化できれば、列バッチ上で評価する。
4. 述語全体をコンパイルできなくても AND の一部をコンパイルできれば、その項で候補を絞る。
5. 残った式を行単位の AST 評価へ戻す。

生存位置を `SelectionVector` に集め、最後に `AppendGather` でまとめて出力バッチへコピーする。入力バッチの順番で添字を追加するため、相対順序を保存する。

### 1.2 JIT の安全条件

JIT 比較は、符号付き 64 ビット整数の格納配列を直接読む。そのため、次の条件をすべて満たす場合に限って使う。

- スキーマと実行時列がともに符号付き `INT64`。
- 定数も符号付き整数。
- `NULL` がない。
- バッチの列レイアウトが期待スキーマと一致する。

符号なし整数に符号付き比較を使うと、`INT64_MAX` より大きい値の順序が反転する。そのため、符号なし整数はバイトコードで評価する。JIT コンパイルに失敗した場合も、一般経路へ切り替える。

### 1.3 許容的な AND 評価

AND の一項が `FALSE` または `NULL` なら、ほかの項の値にかかわらず、その行は除外される。この場合、別の項で発生した式エラーは結果を変えないため、エラーを抑制できる。どの項も行を除外せず、一項の評価に失敗した場合は、`Selection` 全体を失敗させる。

バッチ処理でもこの規則を保つ必要がある。述語全体のバイトコード評価に失敗した場合は、直ちにエラーを返さず、AND の項ごと、行ごとの評価へ切り替える。

### 1.4 費用

ストリーミングで、時間は概ね `O(N × 述語費用)`、追加メモリは入力・出力バッチと選択ベクトル分である。ゾーンマップで除外できるバッチは行式を評価しない。

## 2. `Projection`

`Projection` は各入力行について名前付き式列を評価し、新しい行を作る。入力行数と相対順序は変えず、`RowPosition` を出力へ引き継ぐ。列数、列名、型は出力式で変わる。

### 2.1 式ごとの実行経路

構築時に各式をバイトコード化する。バッチを受け取ると、式ごとに次を選ぶ。

- コンパイル済み式は列バッチ上のバイトコード評価。
- 条件を満たす整数のアフィン式 `column * multiplier + addend` は、十分な行数を処理した後に JIT 評価。
- 対応できない式は行単位 AST 評価。

JIT を使えるのは、符号付き `INT64` で `NULL` がなく、列の配置が期待どおりの場合に限る。乗算または加算のオーバーフローは検出し、一般の式評価と同じエラーにする。検査機能を持たないカーネルを使う場合は、別にスカラーのオーバーフロー検査を加える。

### 2.2 共通部分式除去

複数の出力式に同じ安全な部分式が 2 回以上現れる場合、一時列 `$cse0`, `$cse1`, … を入力バッチへ付加し、各出力式から参照する。

対象は、評価回数を変えても結果が変わらない決定的な二項式、単項式、`CASE` などに限る。一時式をバイトコード化できない場合は、共通部分式として扱わない。共通部分式用の列を加えたバッチでは、元の列と一時列から行を組み直す必要があるため、アフィン式の JIT 評価を使わない。

### 2.3 費用

ストリーミングで、時間は `O(N × 出力式費用)`、追加メモリは入出力バッチと一時列分である。幅を狭める射影を走査や結合より下へ置くと、その後のコピー、ハッシュ、整列、スピル量を減らせる。

## 3. `LimitExecutor`

`LimitExecutor` は最初に `offset` 行を子から読み捨て、その後最大 `limit` 行を返す。返す行の値、位置、順序は変えない。

処理は完全にストリーミングである。必要な行数を返すと子の読み出しを止め、`early_stop` と、実際に子から読み出した行数を診断情報へ記録する。子が走査、選択、射影だけなら、残りの入力を処理せずに済む。子が `Sort` または `Window` の場合は、これらが最初の行を返す前に全入力を読み終えているため、下位の処理量は減らない。

この物理演算子では `limit = 0` を「上限なし」と解釈する。SQL の `LIMIT 0` を表すには、計画生成側で空結果などへ変換し、値 0 をそのままこの演算子の有限上限として渡さない。

`offset` 行の読み捨て中または通常の読み出し中に子が止まった場合は、子の失敗状態を転送する。

## 4. `MaterializeExecutor`

`MaterializeExecutor` は、最初に呼び出されたときに子を末尾まで読み、`(Row, RowPosition)` の配列へ保存する。その後は、この配列から行またはバッチを返す。`Rewind` は読み出し位置を 0 に戻すため、子を再実行せずに同じ内容を再走査できる。

全入力を保存してから出力を始めるため、明示的なパイプラインブレーカーである。

```text
初回 Next
  └─ 子を末尾まで読む
       └─ 行と位置をメモリへ保存
  └─ 保存配列の先頭を返す

Rewind
  └─ 子は再実行せず保存配列を先頭から読む
```

保持量は行の概算サイズ、位置、配列要素の管理費を作業メモリへ計上する。現在の実体化先はメモリだけであり、この演算子自身はディスクへスピルしない。したがって、大きな入力へ無条件に置くと `O(N × 行幅)` のメモリを使う。

子の `Next` が `false` を返すと、その時点の子の状態を自身へコピーしてから、実体化済みと記録する。子が途中で失敗しても、それまでに得た部分配列は残り、同じ呼び出しまたは `Rewind` 後に読み出せる。ただし、演算子の状態は失敗のままであり、この配列は完全な結果ではない。行位置と入力順序は保存する。

## 5. `Max1RowExecutor`

`Max1RowExecutor` は、スカラー副問い合わせが複数行を返さないことを確認する。最初の呼び出しでは子の最初の行をそのまま返す。次の呼び出しで子からさらに 1 行を取得した場合は、「複数行」エラーを記録する。

- 0 行なら 0 行のまま終了する。`NULL` 行の注入はこの演算子の仕事ではない。
- 1 行ならその行と位置を保存して返す。
- 2 行目が観測された時点で失敗する。

複数行かどうかは 2 行目を読んだ時点で分かるため、呼び出し側はストリームの末尾まで読み出す必要がある。スカラー副問い合わせの上位評価も、この条件を前提とする。

## 6. 透過ラッパー

### `RelationRenameExecutor`

関係名の変更を物理計画の表示に残すためのラッパーである。行 API とバッチ API を子へ転送し、値、列配置、順序、行位置を変更しない。子が停止したときは、そのエラーも親へ伝える。名前の変更は、名前解決済みスキーマ上の論理的な境界を表しており、実行時に行を変換する処理ではない。

### `IndexSkipScanExecutor`

内側の `SkipScanDistinct` などを転送し、計画表示上のアクセス方式名を明確にする。重複を飛ばす処理自体は内側が行う。

### `RetainedExecutor`

物理計画は、カタログオブジェクトや表・索引への参照を、コンパイル済み計画から得ることがある。同じ問い合わせ指紋のキャッシュ項目を別の計画で置き換えても、実行中のカーソルが参照する計画は破棄できない。`RetainedExecutor` は、内側の実行器とコンパイル済み計画を共有所有し、両者の寿命を一致させる。行処理、バッチ処理、説明表示は、すべて内側の実行器へ転送する。

`GetStatus` も内側の状態をそのまま返す。破棄時には、参照を利用する内側の実行器を先に破棄し、その後でコンパイル済み計画への参照を解放する。この順序になるように、メンバーの宣言順を定めている。値、順序、位置、計算量は変えず、参照先の寿命だけを保証する。

この種のラッパーによる処理時間の増加は小さい。ただし、子の状態を転送しなければ、子の失敗と正常な末尾を区別できない。`GetStatus` を子へ転送するか、停止時に子の状態を明示的にコピーする必要がある。

## 7. `CardinalityProbe`

`CardinalityProbe` は、子を呼び出す前後で時刻を取得し、返された行数と累積経過時間をナノ秒単位で記録する。行 API では、行を一つ取得するたびに 1 を加える。バッチ API では、返された行数を加える。行の値、バッチ、順序、位置は変更しない。

推定行数が正なら、診断表示に次の倍率を出す。

```text
max(actual, estimated) / max(min(actual, estimated), 1)
```

推定値が 0 以下の場合は、実測行数そのものを誤差値として返す。計測時間には、子の処理時間に加えて、呼び出しに伴うわずかなオーバーヘッドも含まれる。

このラッパーは子の返り値をそのまま返し、自身の独立した失敗は作らない。子の詳細な失敗を診断する側では、子の状態も併せて扱う必要がある。

## 8. `ScheduledExecutor`

`ScheduledExecutor` は、問い合わせ単位の CPU・メモリ利用許可を、実データを処理する直前に取得する。

- 構築だけでは資源を予約しない。
- 最初の `Next` / `NextBatch` で FIFO スケジューラから利用許可を取得する。
- 子が 1 行以上を返す間は同じ利用許可を保持する。
- 子が正常な末尾または失敗によって 0 行を返すと、利用許可を解放する。
- 親が早期停止してオブジェクトを破棄しても RAII で解放する。

行の計算は子に任せ、物理計画の表示には要求する CPU スロット数とメモリ量を加える。計画木全体で一度だけ予約するため、各ノードが同じ資源を重複して予約し、自身の予約待ちで停止する事態を避けられる。

このラッパーは子の `GetStatus` を転送せず、子が 0 行を返した時点で利用許可を解放するだけである。失敗と正常な末尾を区別するには、内側の演算子の状態も確認する必要がある。

## 9. `UnnestExecutor`

`UnnestExecutor` は各外側行について配列式を評価し、配列要素ごとに 1 行を作る。

```text
入力:  (id=7, a=[10,20,30])
出力:  (7,10), (7,20), (7,30)
```

処理手順は次のとおりである。

1. 子から外側行を 1 行取る。
2. その行を評価範囲として UNNEST 式を評価する。
3. 配列値を一時的な関係へ変換する。
4. 要素行を計画上の出力スキーマへ列名で整列する。
5. 外側行と要素行を連結して順に返す。

`WITH OFFSET` があれば、0 から始まる要素位置を追加する。配列要素が構造体の場合は、各メンバーを列へ展開できる。実行時の値がスカラー、`NULL`、構造体のいずれであっても、宣言済みの列名に合わせ、存在しない列を `NULL` で補う。

宣言された配列要素型が DATE で、実行値に日付文字列が残っている場合は、展開境界で DATE 値へ正規化する。これにより、一つの列バッチ内で行ごとに型が変わることを防ぐ。

通常の `UNNEST` では `NULL` または空配列から 0 行を作る。左外部モードでは外側行を失わないよう、要素側を全 `NULL` にした 1 行を作る。生成行は複数の値から合成されるため、外側の `RowPosition` を引き継がず無効位置を返す。

外側行数を `N`、各配列長を `a_i` とすると、出力行数と時間の下限は `Σ a_i` である。演算子は一つの外側行の展開結果だけを保持し、外側入力全体は実体化しない。
