# 走査と行生成

走査は物理計画の葉に位置し、格納済みのデータまたは生成したデータを上位の演算子へ返す。どのアクセス方式でも、スナップショットに対する可視性、残余述語、物理行位置、順序保証を扱う。

## 1. アクセス方式の選択

| 方式 | 主な費用 | 順序 | 適する条件 |
|---|---|---|---|
| 全走査 | `O(N)` | 通常は物理走査順 | 表の大部分を読む、利用可能な索引がない |
| 並列全走査 | `O(N/P)` に調整費用を加える | ワーカー完了順 | 大きな表、順序不要、更新ロック不要 |
| B+Tree 範囲走査 | `O(log N + M)` | キー昇順または降順 | 等値、範囲、順序利用、高選択度 |
| ビットマップ・ヒープ走査 | 索引候補作成と位置順ヒープ I/O | 物理行位置順 | 複数索引条件の AND/OR、中程度の選択度 |
| TID 走査 | 指定位置数に比例 | 指定位置を整列した順 | 物理行位置が既知 |
| スキップ走査 | 異なるキーの数に概ね比例 | 索引キー順 | 索引上の重複を飛ばす重複除去 |

ここで `M` は、指定範囲に含まれる索引項目数である。索引が存在していても、その定義が現在の表定義と一致しなければ利用できない。その場合は、表走査に残余選択と必要な射影を組み合わせる。

## 2. `FullScan`：表の全走査

`FullScan` はトランザクションの表反復子を先頭から進め、可視な行と `RowPosition` を返す。行 API とバッチ API の両方を持ち、バッチ API は一度に指定行数まで `DataChunk` へ追加する。

構築時に最大行数を受け取れる。既定は実質的に無制限で、上限に達すると下位の反復子をそれ以上進めず終了する。これは計画上の一般的な `LIMIT` とは別に、走査自身へ設定する物理的な上限である。

更新対象を探す走査では行をロックし、書き込み意図を取得できる。競合時に待つ方式と、取得できなければ競合エラーにする方式がある。通常の読み取り走査はこれを行わない。

反復子が無効になったときは、その理由を確認する。正常に末尾へ達した場合だけ成功とし、ページ取得や I/O が途中で失敗した場合は、最初のエラーを保持して親へ伝える。

特性は次のとおりである。

- ストリーミングで、追加作業メモリは 1 バッチ程度。
- 時間は表の可視候補行数に対して `O(N)`。
- 行位置を保存する。
- 上位に明示的な順序保証を提供しない。

## 3. `ChunkedScan`：モーセル単位の走査

モーセルとは、ワーカーや実行ループが処理する小さな走査範囲である。表モードの `ChunkedScan` は、複数のページを一つのモーセルにまとめて順番に走査する。問い合わせ全体を一つの仕事にせず、数ページ単位に分割することで、ワーカー間で仕事を分配できる。

構築時には、出力する列番号と任意のフィルタを指定できる。ストレージ反復子は必要な列だけを作り、`VectorizedExpression` がフィルタをバッチ単位で評価する。条件を満たした行は、選択ベクトルに従って行位置とともに出力バッチへコピーされる。

索引モードでは、指定範囲の索引反復子から最大バッチ幅まで読み、同じベクトルフィルタを適用する。表モードのページモーセル分割とは異なり、一つの索引カーソルを順次進める。

行 API は内部でバッチ API を呼び、保持したバッチから 1 行ずつ返す。したがって、どちらの API でもフィルタ意味論は同じである。

フィルタ式の評価に失敗した場合は、そのエラーを保持する。一方、索引反復子とモーセル反復子が無効になったときは `GetStatus` を確認しない。ストレージ障害が例外を発生させず反復子の状態だけに記録された場合、索引範囲の終了または次のモーセルへの移行として扱われる。その結果、途中までの入力を正常な全入力と誤認する可能性がある。

## 4. `ParallelScan`：並列表走査

`ParallelScan` は、表をページ単位のモーセルへ分割する。各ワーカーは、共有アトミックカウンタから次のモーセル番号を取得する。範囲をあらかじめ等分しないため、空きページや可視行数に偏りがあっても、処理を終えたワーカーが次のモーセルを担当できる。

各ワーカーは次の順に動く。

1. 共有カウンタから次のモーセルを取得する。
2. 任意の列射影と、整数列をページ上で先読みする比較条件を設定して反復子を開く。
3. 1024 行単位の `DataChunk` を作る。
4. ページラッチを解放する。
5. 完成バッチを有界キューへ入れる。

キュー上限は少なくとも 2、通常はワーカー数の 2 倍である。キューが満杯ならワーカーは待つが、その前にページラッチを落とす。消費側の `max_rows` がワーカーの固定バッチ幅より小さい場合は、一つの受信バッチを内部に保留し、複数回に分けて返す。

物理特性は次のとおりである。

- バッチ内部では走査順を保つが、バッチ間はワーカー完了順なので全体順序を保証しない。
- 射影と行位置を保存する。
- 親が早期停止して演算子を破棄すると、停止フラグを立て、キューで待つワーカーを起こし、全ワーカーの終了を待つ。
- 最初のワーカー例外を実行状態へ変換し、正常な末尾に見せない。
- 更新ロック、走査固有の最大行数、順序要求がある場合は並列走査にしない。

ワーカー内で発生した例外は、共有の実行エラーへ変換する。ただし、各モーセル反復子の `IsValid()` が偽になった後に `GetStatus` を確認しない。例外を発生させず反復子の状態だけに記録された障害は、そのモーセルの正常終了と区別されない。

大きな表で推定行数が閾値を超え、上の制約がなければ全走査の代わりに選べる。

## 5. `IndexScan`：範囲索引走査

`IndexScan` は B+Tree の開始キーと終了キーからカーソルを開き、昇順または降順に進める。キーは 1 列値だけでなく複合キーの値列を受け取れる。出力は索引キーだけでなく、索引項目が指す可視な表行全体である。

`IN` 条件などでは、互いに離れた複数の範囲を一つの演算子に指定できる。一つの範囲を読み終えると次の範囲のカーソルを作り、すべての範囲を順に処理する。範囲はキー順に並ぶため、同じ区間を重複して探索せずに済む。

索引条件だけで述語全体を表せない場合、候補行に残余述語を評価する。AND の各項を許容的に評価し、SQL のフィルタ規則で `TRUE` だけを返す。式評価自体に失敗した場合は走査を失敗させる。

更新用モードでは、索引が指した `RowPosition` に書き込み意図を取得する。待機なしモードで取得できなければ競合エラーになる。可視でなくなった無効行は飛ばす。

反復子の途中失敗は範囲終了と区別する。失敗した範囲の後に保留範囲があっても、次へ進まず全体を失敗させる。

期待計算量は `O(log N + M)` であるが、表行取得がランダム I/O になる場合は `M` の定数が大きい。出力は指定方向の索引キー順で、行位置を保存する。

## 6. `IndexOnlyScan`：索引のみ走査

`IndexOnlyScan` は索引キー列と INCLUDE 列だけを出力する。出力スキーマは `key columns + include columns` であり、表の他の列を組み立てない。残余述語もこの出力スキーマに対して評価する。

索引項目だけでは MVCC 可視性を判定できないため、各項目が指すヒープ行を確認し、不可視または無効な行を除く。INCLUDE 列も、可視なヒープ行から取り出す。したがって、ここでの「索引のみ」とは、出力列を索引キーと INCLUDE 列に限ることを指す。ヒープへ一切アクセスしないという意味ではない。

行位置は外側へ公開せず、行 API に渡された `RowPosition` 出力先も書き換えない。直接呼び出す側は、以前の有効位置が残った変数を結果位置として再利用してはならない。結果の順序は索引の昇順または降順である。索引定義が古い場合は、表走査、選択、対応列の射影へ戻す。

索引反復子が無効になった後に `GetStatus` を確認しないため、この走査は `IndexScan` と異なり、反復子の途中失敗と正常な末尾を区別しない。残余式の失敗は保持されるが、索引読み出しの失敗が反復子の状態だけに記録された場合は、部分結果を正常な全結果と誤認する可能性がある。

## 7. `BitmapIndexScan` と `BitmapHeapScan`

`BitmapIndexScan` は行を返す要求駆動型演算子ではなく、索引範囲を `RowPosition` の集合へ変換する部品である。得た位置を物理位置順に整列し、重複を除く。

この部品には、索引反復子の終了状態を返す経路がない。反復子がエラー状態で途中停止しても、それまでに集めた位置集合を返す。

複数条件は位置集合で合成できる。

- AND は整列済み集合の積を取る。
- OR は整列済み集合の和を取り、重複を除く。

`BitmapHeapScan` は、合成済みの位置を改めて整列して重複を除き、物理位置順に表を読む。索引条件が候補を過剰に含む場合や、MVCC の状態が変わる場合に備えて、任意の残余述語を表の行に対して再評価する。読み出せない位置は飛ばし、式評価の失敗だけを保持する。

位置順に読むと、複数の索引範囲から表を個別にランダムアクセスする場合より、近い位置を続けて読みやすい。ただし、候補位置を先に全件保持するため、最初の行を返すまでの時間と位置配列用のメモリが必要になる。

## 8. `TidScan`：行位置の直接走査

`TidScan` は明示された `RowPosition` 列を順に読み、対応する可視行を返す。指定位置を読み出せない場合はその位置を飛ばす。成功した行には元の位置を添える。

候補数を `T` とすると処理回数は `O(T)` だが、位置順でなければランダム I/O になりやすい。ビットマップ走査のような集合生成は行わず、上位が指定した位置列をそのままアクセス要求として使う。

## 9. `SkipScanDistinct` と `IndexSkipScanExecutor`

`SkipScanDistinctExecutor` は `SkipScanDistinct` の公開別名であり、独立した実行方式ではない。

通常の重複除去は全候補行を読み、既出値の集合または直前の行と比較する。`SkipScanDistinct` は B+Tree のキー境界を使う。一つのキーから代表行を返した後、そのキーに属する残りの位置、または同じ接頭辞を持つキーをまとめて飛ばす。

索引キー全体で重複を除く場合、現在の B+Tree 項目から次の項目へ移るだけで同一キー下の複数行を飛ばせる。先頭 `k` 列だけで重複を除く場合は次のように動く。

- 昇順では、現在の接頭辞を memcomparable 形式（バイト列の比較順が値の比較順と一致する形式）に符号化し、上限番兵を加えたキーまでカーソルを進める。
- 降順では、同じ接頭辞が続く間カーソルを後退させる。

一意索引でも `NULL` を含むキーは SQL 上互いに等しくないため、複数位置を持つ形式で格納される。その形式を判別して代表の位置を得る。代表行はヒープから解決して可視性を確認し、残余述語を評価する。

出力は異なるキーごとに最大 1 行で、代表行の位置を保存する。残余述語が代表行を落とした場合、そのキーの別行を試さず次のキーへ進む。このため、述語を適用した後の任意行代表ではなく、索引代表行へ適用するアクセス方式として計画する必要がある。

`IndexSkipScanExecutor` は内側の走査をそのまま転送し、計画表示で `IndexSkipScan` という物理境界を示すラッパーである。独自の重複除去アルゴリズムは持たない。

ページ取得と索引値の復号に失敗すると、走査固有の状態にエラーを保存する。一方、残余述語の評価エラーは基底クラスの状態に保存されるが、この走査の `GetStatus` は走査固有の状態を返す。このため、残余述語のエラーで走査が停止しても、そのエラーを `GetStatus` から取得できない。直接利用する場合は、このエラー伝播の制約を考慮する必要がある。

## 10. `MinMaxIndexExecutor`

`MIN` または `MAX` の対象列で順序付けられた入力を受け、指定列の最初の非 `NULL` 値を 1 行だけ返す。`MIN` なら昇順、`MAX` なら降順の索引走査を子にすることで、表全体の集約を先頭探索へ変えられる。

入力が空、または全値が `NULL` なら、`NULL` を一つ持つ行を返す。これはグループなし集約が空入力でも 1 行を返す規則に対応する。出力は新しい集約行なので物理行位置を持たず、行 API に渡された `RowPosition` 出力先も書き換えない。

この演算子は、子が `false` を返した理由を調べずに `NULL` 行を生成し、子のエラーを自身の状態へ転送しない。そのため、子の失敗と空入力または全 `NULL` の入力が、同じ結果になる。呼び出し側で子の状態を別に確認する必要がある。

## 11. 定数、空行、および数列の入力

この節の演算子が生成する値は、格納済みの行に対応しない。`ValuesExecutor`、`ConstantExecutor`、`GenerateSeriesExecutor` の行 API は、渡された `RowPosition` を書き換えない。直接呼び出す場合は、以前の有効位置が残った変数を再利用できない。既定のバッチ変換は、行ごとに新しい無効位置を作る。

### `ValuesExecutor`

明示された定数行列を保持し、構築時の順に一度だけ返す。小さな `VALUES` 句の物理入力として使う。入力値は所有権を移して返すため、先頭へ戻って繰り返し読める共有表ではない。

0 列の行を 1 行持つ `ValuesExecutor` は、ダミー走査として使える。`SELECT 1` のように `FROM` がない問い合わせでも、上位の射影をちょうど 1 回評価するための単位関係になる。

### `ConstantExecutor`

保持済みの行列を同様に返すが、計画表示に任意のラベルを付けられる。定数関係や診断上の物理葉を表す。データの生成方式は `ValuesExecutor` とほぼ同じである。

### `EmptyResultExecutor`

常に 0 行を返す。矛盾した述語、空集合との結合、空な枝の簡約結果を、下位を実行せず表現する。失敗ではなく正常な空ストリームである。

### `GenerateSeriesExecutor`

`start` から `stop` まで、`step` ずつ増減する 64 ビット整数列を生成する。条件を満たす場合は `stop` も含む。`step` が正なら現在値が `stop` を超えるまで、負なら `stop` を下回るまで生成を続ける。

- `step = 0` は不正引数エラー。
- 加算が 64 ビット整数の範囲を超える場合は、それ以上値を作らず正常終了する。
- 行は生成物なので物理行位置を持たない。

## 12. `RemoteScan`：遠隔入力

`RemoteScan` には二つの入力形態がある。

1. あらかじめ保持された `DataChunk` 列。
2. 生産側がバッチまたは単一行を追加し、最後に閉じる共有チャネル。

バッチ API は、チャネルから一つのバッチを受け取るまで待ち、そのバッチをそのまま返す。バッチを取得できない場合は、行 API を使って指定行数まで出力を組み立てる。行 API は、まず内部に保持しているバッチを読み、次のバッチを受信した後に単一行キューを調べる。

生産側は通常、バッチ方式と行方式のどちらかに統一する。行方式だけを使う場合は、チャネルを閉じてバッチ待ちを解除する必要がある。

チャネルを閉じた後、キューが空になると正常終了する。受信した `RowPosition` はそのまま返す。ネットワーク通信、再送、チェックサム、遠隔エラーの符号化は、この演算子では扱わない。ここで提供するのは、スレッド安全な受信境界だけである。

チャネルが表現できる終端は、正常な閉鎖だけである。独立したエラー状態はない。生産側または通信処理の失敗を伝えるには、外側のプロトコルにエラー表現を用意する必要がある。

## 13. `AnalyzeScan`：統計収集走査

`AnalyzeScan` は子演算子、または指定表の全走査を一度だけ完全に読み、列統計を構築する。出力は解析した総行数を持つ 1 行である。任意で完成した統計をカタログへ保存する。

各列について次を求める。

- `NULL` 数と非 `NULL` 数
- HyperLogLog による異なる値の数の推定
- リザーバサンプリング（reservoir sampling）による固定上限の標本
- 実数え上げによる頻度上位 5 値
- 標本中の最小側・最大側それぞれ最大 5 個の異なる値
- 標本をほぼ等しい個数へ分けたヒストグラム

リザーバサンプリングは、入力行数を事前に知らなくても、各行を同じ確率で固定サイズの標本に含める。ヒストグラムの各区間は、標本内の下限、上限、異なる値の数、および全非 `NULL` 行数へ拡大した推定件数を持つ。

現在の方式は、統計計算を始める前に全行を配列へ保持する。基本的な計算量は時間 `O(N + C N)`、メモリ `O(N)` である。ここで `C` は列数を表す。値の頻度表も、各列の異なる値の数まで増える可能性がある。

`AnalyzeScan` は通常の結果走査と異なり、全入力を保持して一度だけ実行する保守用の演算である。

現状では、子走査または内部全走査が `false` を返した理由を確認せず、その時点までの行から統計を完成させる。また、カタログへの統計保存が返す状態も取り込まない。そのため、下位の失敗が短い入力として扱われ、部分入力の統計と件数行が正常に見える可能性がある。完全性を必要とする呼び出し側は、下位走査と保存処理の成功を別の境界で保証する必要がある。
